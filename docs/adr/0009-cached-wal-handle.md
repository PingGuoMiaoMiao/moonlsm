# ADR-0009：常开一个追加句柄 —— 单条 `put` 的 6 倍

- **状态**：已采纳
- **日期**：2026-10-26
- **相关**：ADR-0004（存储抽象）、ADR-0005（组提交）、`docs/engineering/BENCHMARK.md` §2

---

## 背景

ADR-0005 把「一批写入只 `fsync` 一次」做完了，组提交的收益拿到了，
但单条 `put` 一直停在 `76 ops/s`（13.2 ms/条）。这个数字在
`BENCHMARK.md` 里挂了三天，也被写进了申报书的「已知短板」：
SQLite 同一场是 `498 ops/s`，差 6.5 倍。

根因 ADR-0005 已经量出来了：Windows 上单次 `fopen`/`fclose` 约 5.9 ms，
且与写入字节数无关。只是当时只修了批量路径 —— 因为 `crash_test.py`
一轮只能写 200 条，问题太显眼。单条路径留了下来。

拆一下 13.2 ms 花在哪。`Db::put` 走两步：

```
append_wal_frame  →  Storage::append_file  →  fopen("ab")  … fclose
sync              →  Storage::sync_file    →  fopen("rb+") … fsync … fclose
```

每条写开关两次文件。ADR-0005 当时的归因是「一次 `fopen`/`fclose` 5.9 ms」，
按这个算 2 次就是 11.8 ms，占总成本的九成。

**这个归因今天复现不出来。** 用 Python 把两条路径拆开量（同一台机器，
300 次迭代，200 字节/次）：

| 路径 | ms/次 |
|---|---:|
| 只 `fopen("ab")` + 写 + `fclose` | 0.83 |
| 只 `fopen("rb+")` + `fsync` + `fclose`（文件刚被写过） | 1.11 |
| 两步合起来（旧路径） | **9.88** |
| 常开句柄：写 + `fflush` + `fsync`（新路径） | **2.07** |

两步单独量的和是 1.94 ms，合起来却是 9.88 ms —— **5 倍的差额来自
「关掉写句柄，再重新打开去 fsync」这个组合，不是两次 `fopen` 本身。**

具体是 Windows 的缓存一致性（带写权限打开一个刚写过、已进缓存的文件会
触发一次刷写），还是杀软在 `fclose` 后重扫，我没有证据区分，所以这里
只陈述测量结果，不编机制。能确定的是：**旧路径每条写多做了一次
「关闭 → 重开 → 刷写」，这部分是可省的。**

---

## 决策

`NativeStorage` 持有**一个**常开的追加句柄，写和 `fsync` 都复用它。

### 为什么只有一个

写路径上反复打开的只有活跃 WAL。SST / MANIFEST / CURRENT 是一次成型文件，
缓存它们只会多出「什么时候失效」的状态，换不到吞吐。

一个句柄的失效规则可以逐条列完，不会出现「表里某个条目忘了失效」的漏洞 ——
而这类漏洞在 Windows 上的表现是「删不掉 / 改不了名」，只在特定顺序下出现。

### 失效规则：三个操作无条件关，不判断文件名

| 操作 | 处理 | 理由 |
|---|---|---|
| `write_file` | 先 `close_handle()` | 截断与「另一个还开着的句柄」混用不可推理：追加位置、CRT 缓存的文件长度都可能停在旧值 |
| `rename_file` | 先 `close_handle()` | Windows 不允许改名一个被自己打开的文件（sharing violation）；POSIX 允许，但会让「改名后旧句柄继续写」变成静默的数据错乱 |
| `remove_file` | 先 `close_handle()` | 同 rename。`flush()` 删旧 WAL 时一定走到，而旧 WAL 正是缓存里的那个 |

「不判断文件名」是刻意的：这三个操作很少发生，多关一次的代价只是一次
`fopen`；漏关一次的代价是平台相关的、难复现的数据错乱。

### 语义没有变

- `append_*` 仍然**不隐含** `fsync`。`sync_file` 仍然是 C1 的唯一实现点。
- 每次追加后立刻 `fflush`。常开句柄意味着数据会跨调用留在 stdio 缓冲里，
  不刷的话另开句柄的 `read_file` 看不到刚写的字节 —— 而恢复路径正是
  「写完 WAL 立刻读回来」。
- 写失败 / `fsync` 失败后关掉句柄再抛错：部分写入 + 错误标志的 `FILE*`
  不该继续用。
- `sync_file` 命中缓存时复用 fd；没命中时仍是「打开 → fsync → 关闭」，
  所以「对不存在的文件 fsync 要报错」这条行为原样保留。

### 崩溃语义为什么没变

`kill -9` 杀掉进程，丢的是**进程内**缓冲；页缓存属于 OS，不随进程死。
每次追加都 `fflush` 过，所以 `kill -9` 之后 WAL 里该有的字节一个不少，
和 `fclose` 版本一致。真正的持久化保证仍然只由 `fsync` 提供 ——
这条边界没有被这次改动移动，`crash_test.py` 20 轮就是它的验收。

### 代价：进程退出前有一个句柄没关

`Db` 没有 `close()`（v1 的 API 面里没有），所以缓存句柄会活到进程结束，
由 OS 回收。一个句柄，不是泄漏累积。需要确定性释放的场合（测试收尾、
工具里反复开关数据目录）调 `NativeStorage::close()`。

`examples/basic` 与 `cmd/dbcli` 都是短进程，不加 `close()`。

## 实测（同场 A/B，同一台机器背靠背跑）

用 `git` 取出改动前的二进制冻结成 `dbcli-base.exe`，与新二进制交替跑，
数据目录各自独立。**不跨会话比数字** —— `BENCHMARK.md` §5 记过，
同一份代码隔一天能差 26%。

### 单条提交（`--n 2000 --batch 1 --sync`）

| 轮次 | 基线 | 常开句柄 |
|---|---|---|
| 1 | 56 ops/s（17.9 ms/条） | **384 ops/s**（2.60 ms/条） |
| 2 | 64 ops/s（15.6 ms/条） | **399 ops/s**（2.51 ms/条） |
| 随机写 1 | 80 ops/s | **476 ops/s** |
| 随机写 2 | 83 ops/s | **475 ops/s** |

**约 6.3×**，每条从 15.6–17.9 ms 降到 2.5–2.6 ms。

> 文档里原来那个 13.2 ms 是 10-22 测的，今天这台机器上基线是 15.6–17.9 ms。
> 跨会话不可比，所以这里只报同场的比值，不报「从 13.2 降到 2.5」。

按文档里 SQLite 的 `498 ops/s`（2.0 ms）作参照，差距从 6.5× 缩到约 1.3× ——
两个数字不同场，只能看量级，不能当结论。

**一组反证**：把 `sync` 关掉（`--batch 1`，不等 fsync）再比一次，
两版几乎一模一样 —— 基线 1 952 ops/s、新版 1 946 ops/s（随机写
7 724 / 8 027）。也就是说**追加路径的 `fopen`/`fclose` 本来就不贵**
（0.5 ms 上下），收益全部来自 `sync_file` 那一段。这既印证了归因，
也说明 ADR-0005 里「每次 `fopen` 5.9 ms」这个常数不该被当成通用值引用。

### 组提交（`--n 200000 --batch 1000 --sync`）

| 指标 | 基线 | 常开句柄 | 变化 |
|---|---|---|---|
| 顺序写 | 21 359 / 21 714 / 23 008 ops/s | 31 402 / 30 410 ops/s | **+42%** |
| 随机写 | 11 832 / 12 507 / 12 788 ops/s | 15 443 / 17 039 ops/s | **+37%** |
| 范围扫描 | 52 759–58 274 rows/s | 52 910–82 802 rows/s | 噪声内 |
| 空间放大 | 1.83× | 1.83× | 不变 |

组提交那组本来就只有「每 1000 条两次 `fopen`」，所以收益远小于单条路径 ——
11.8 µs / 46.8 µs ≈ 25%，实测 37–42%（`fopen` 成本今天偏高）。
**收益大小与「每条写打开几次文件」严格相关**，这从反面印证了归因。

### 读路径：没变，也没有「顺手变快」

完整基准里先写后读，两版的读 P50 差了近 40%（0.114 → 0.065 ms），
但读路径一行没改。为了判断这 40% 是真的还是写阶段留下的进程状态，
另做了只读对照：**同一份数据的两个副本**，各开一个 dbcli，发同样的
40 000 次读（20 000 命中 + 20 000 未命中）。

| 场景 | 基线 P50 | 常开句柄 P50 |
|---|---|---|
| 命中 | 0.043 ms | 0.061 ms |
| 未命中 | 0.063 ms | 0.062 ms |

**没有差别**，命中的方向甚至还相反。所以完整基准里那 40% 是进程状态残留
（写阶段开了几千次文件之后的状态），不是读路径的收益 —— 本次**不宣称**
任何读延迟改善。工具留在 `benches/python/read_ab.py`。

## 后果

- `moonlsm` 0.2.2。单条 `put` 的短板从「6.5 倍」变成「同一量级」，
  `BENCHMARK.md` §2、申报书的「已知短板」同步更新。
- v1.1 的「WAL 句柄缓存」技术债关闭。剩下的两条（data block CRC、
  SST footer 存 smallest_key）不动。
- 新增 7 条 `fs_native_wbtest` 用例，测的不是「快了多少」，而是
  「缓存了句柄之后，原本靠 `fopen`/`fclose` 隐式保证的事情还成不成立」：
  截断 / 删除 / 改名之后追加位置、`fflush` 的可见性、该报错的地方还报错。
