# ADR-0005：组提交 —— 一批写入只 fsync 一次

- **状态**：已采纳
- **日期**：2026-10-20
- **相关**：ADR-0003（崩溃一致性契约 C1–C5）、ADR-0004（存储抽象）

---

## 背景

`Db` 接上真文件系统后端（ADR-0004）之后，`crash_test.py` 每轮（约 2–3 秒）
只能写入 **200 条**。这个数字不足以支撑任何演示，也说明有严重的实现问题。

拆解下来是两个独立的原因，叠在一起：

| 原因 | 单条成本 | 200 条批次 |
|---|---|---|
| 每条 `put` 单独 `fsync` | — | 200 次刷盘 |
| 每次追加单独 `fopen`/`fclose` | 约 5.9 ms | 约 1180 ms |

第二个才是主因。实测数据（Windows，200 条 × 200 字节 value）：

```
batch=1     200 批  总 1175 ms   每条 5.87 ms
batch=10     20 批  总 1171 ms   每条 5.85 ms
batch=50      4 批  总 1186 ms   每条 5.93 ms
batch=200     1 批  总 1172 ms   每条 5.86 ms
```

**单条成本与批次大小完全无关**，这排除了「数据量」「缓冲增长」之类的解释，
指向一个固定开销：每写一帧就开关一次文件。

更关键的是，把 `sync` 关掉（`"sync": false`）耗时**一点没变**。
也就是说，此时瓶颈根本不在 fsync —— 优化 fsync 次数在这个阶段毫无意义。

---

## 决策

分两层处理，对应两个不同的开销：

### 1. `Storage::append_frames(name, chunks)`：一次 `fopen`，N 次 `fwrite`

新增一个存储原语，语义等价于「对 `chunks` 里每一段依次调用 `append_file`」，
但只打开一次文件。

- `NativeStorage`：一次 `fopen("ab")` + 循环 `fwrite` + 一次 `fclose`
- `MemStorage`：一次性拼接（而不是循环 `append_file`，那会是 O(N²) 字节拷贝）

**等价性是硬要求**，不是「差不多就行」。两个后端实现完全不同，
必须用同一条测试锁住「同样的输入产出同样的字节」
（`storage_wbtest.mbt` / `fs_native_wbtest.mbt` 各一条）。

### 2. `Db` 攒帧，`sync()` 一次写出

`put_deferred` / `delete_deferred` 不再逐帧写盘，而是把编码好的帧推进
`pending` 数组；`sync()` 时调用一次 `append_frames`，再 `sync_file`。

于是 `putmany(200)` 的磁盘操作变成：
**1 次 `fopen` + 200 次 `fwrite` + 1 次 `fclose` + 1 次 `fsync`**。

结果（同一台机器，同一份 workload）：

| 场景 | 之前 | 之后 | 倍数 |
|---|---|---|---|
| `putmany(200)` 带 fsync | 1200 ms | 12 ms | **100×** |
| `putmany(200)` 不带 fsync | 1172 ms | 3 ms | **390×** |
| `crash_test` 单轮写入量 | 200 条 | 50000 条 | **250×** |

---

## 为什么这仍然满足 C1

C1 的原文是：**已确认的写入必不丢**。「确认」= 调用方拿到 ack。
契约从来没有要求「每条写入各 fsync 一次」，只要求 **ack 发出之前 fsync 已经成功**。

```
put_deferred × N   →  内存里攒 N 帧 + 改 memtable     （此时没有任何 ack）
sync()             →  append_frames + fsync            （失败就抛错，不发 ack）
返回 ack           →  调用方认为写成功
```

`crash_test.py` 的 5 轮结果（每轮 2–3 秒、3 万到 5 万条写入）：

```
Round 1: 2.2s, 写入 28000 条, acked 15079, 丢失 0, 半条 0  -> PASS
Round 5: 2.9s, 写入 39200 条, acked 17129, 丢失 0, 半条 0  -> PASS
```

（`acked` 小于写入量是因为 `--key-space 20000`，重复 key 在字典里合并了。）

## 代价：两条写入路径的失败可见性不同

这是本决策唯一需要小心的地方，**必须写进文档而不是靠人记住**。

| | `put` / `delete` | `put_deferred` + `sync` |
|---|---|---|
| fsync 位置 | memtable **之前** | 一批结束之后 |
| fsync 失败时 | 写入**完全不可见** | 数据留在内存里**可读**，但无 ack、断电必丢 |
| 原因 | 单条写可以等 | 写第一条时无法预知最后的 sync 会不会成功 |

所以 `put` 保持自己的顺序（`追加帧 → fsync → 改 memtable`），
**不复用** `put_deferred`。看起来有重复，但这个顺序差异就是语义差异，
合并成一条路径会悄悄丢掉「fsync 失败 ⇒ 完全不可见」这个性质 ——
`db_wbtest.mbt` 里有一条测试专门盯着它（「fsync 失败时 put 必须抛错，
且数据不能进 memtable」）。这个测试在第一次实现组提交时确实失败了。

对 `put_deferred` 的调用方，约定是：**`sync()` 抛错就丢弃这批数据并重新打开数据库**，
不要继续读。

---

## 另一个副作用：`put_deferred` 现在连 WAL 都不写

之前 `put_deferred` 会立即追加到 WAL（只是不 fsync），所以进程崩溃后
那批数据**有可能**还在（OS 迟早会把页缓存写下去）。
现在帧留在内存里，崩溃后**必然**丢失。

这是可接受的：
- 没有 ack 的数据本来就在「允许丢失」的范围内（契约第 2 条）；
- 而且这让行为变得**确定**，而不是「取决于 OS 什么时候回写」——
  确定性对测试友好得多。

代价是 `put_deferred` 之后必须显式 `sync()` 才能让数据进入 WAL。
`dbcli` 的 `putmany` 已经这么做了。

## 备选方案

### A. 在 `NativeStorage` 里维护常开句柄表

每次 `append_file` 复用同一个 `FILE*`，开销从 5.9ms 降到接近 0。

**否决**：MoonBit 没有析构函数，句柄的关闭时机只能靠显式 `close()`。
一旦调用方忘了关（或者中途抛错），fd 就泄漏；而「忘了关」这种 bug
在长跑进程里要几小时才暴露。ADR-0004 已经明确选了「无常开句柄」
来换取状态简单，这里不应该为了性能把它推翻。

### B. 让 `putmany` 自己拼一个大 `Bytes` 再调一次 `append_file`

**否决**：会改变 WAL 的帧边界语义 —— 一个「大 frame」和 N 个「小 frame」
在恢复时的截断行为不同（前者只能整段丢弃）。WAL 的恢复粒度必须是单条记录。

### C. 把 `append_frames` 做成 trait 的默认实现（循环调用 `append_file`）

**否决**：这个工具链的 trait 不支持带默认实现的方法（`Self` 在方法体里
没有绑定名）。而且「默认退化成慢路径」会让忘记覆写的后端悄悄慢 100 倍，
不如让编译器直接报「没实现」。

### D. 只减少 fsync 次数，不碰 `fopen`

**否决**：实测证明无效 —— 把 `sync` 关掉耗时不变，瓶颈完全在开关文件上。
这个方案会让代码变复杂而指标纹丝不动。

## 遗留问题

1. **单条 `put` 仍然是 5.9ms 一次**（一次 `fopen` + 一次 `fsync`，两次开关文件）。
   `model_check.py` 里 45% 的操作是单条 `put`，所以它的速度受此限制。
   真要解决得回到方案 A（句柄表），或者把 `fsync` 和 `fwrite` 合并成
   一次打开（`append_file_synced`）。后者是个更小的改动，留给 Week 3 的性能阶段。

2. **`flush()` 会清空 `pending`**。这是正确的（那些帧的数据已经随 SST 落盘），
   但依赖一个不显眼的前提：`pending` 里的每一帧对应的记录都必须在 memtable 里。
   如果将来引入「不经过 memtable 的写入路径」，这个前提就破了。
   到时候必须在 `flush()` 里加断言。
