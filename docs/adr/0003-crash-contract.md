# ADR-0003：崩溃一致性契约 —— 我们承诺什么，不承诺什么

- **状态**：已接受（Accepted）
- **日期**：2026-10-21
- **决策者**：chendev
- **影响范围**：`wal.mbt`、`db.mbt`、`cmd/dbcli`、全部崩溃测试

---

## 背景（Context）

「LSM 引擎崩溃不丢数据」这句话如果不说清楚，就是一句无法验证的营销话术。要让它变成可验收的工程承诺，必须先回答三个问题：

1. **丢什么、不丢什么？** —— 是「一条都不能丢」还是「确认过的不能丢」？
2. **怎么测？** —— `kill -9` 到底能证明什么？
3. **测不出来的时候怎么办？** —— 有些失效模式在当前测试手段下不可观测，是假装不存在，还是明说？

第 2 个问题是关键，因为这里存在一个**广泛流传的误解**：

> 「我写了 100 万条，`kill -9`，重启后一条不少，所以我的持久化是对的。」

**这个推理是错的。** `kill -9` 只杀死进程，**不清空操作系统页缓存（page cache）**。进程内 `write()` 返回的数据已经进入内核页缓存，即使没有 `fsync`，在重启进程后依然能被读到。因此一个**完全忘记 `fsync`** 的实现，照样能通过 `kill -9` 测试——它测的是「进程内缓冲有没有 flush」，而不是「数据有没有落盘」。

真正能让「忘了 fsync」暴露的，只有两类手段：

- **WAL 尾部截断注入**：模拟「内核只写下去一部分」的物理现实
- **虚拟机 / 硬件断电**（`virsh destroy`、拔电源），清空页缓存

本 ADR 定义契约、明确测试分层，并把「当前测不出来的部分」写进文档而不是藏起来。

---

## 决策（Decision）

### 1. 契约正文（这就是对外承诺的全部内容）

> **C1（已确认必不丢）**：`put` / `delete` / `putmany` 在 `sync:true` 下返回成功后，该操作的效果在任意时刻的崩溃后**必然可见**。
>
> **C2（未确认可以丢）**：`sync:false`（默认）的写入，或已发出但未收到响应的写入，崩溃后**允许丢失**。丢失的单位是「整条操作」，不允许出现「只丢一半」。
>
> **C3（绝不读出错数据）**：任何情况下，读路径**不得返回半条记录**（torn write）、不得返回 CRC 校验失败的数据、不得把不同 key 的字节拼接后返回。宁可返回 `None`，也不返回脏数据。
>
> **C4（绝不静默丢数据）**：恢复过程中若发现无法解释的损坏（非尾部截断），必须返回 `LsmError::Corruption` 或至少产生一条可观测的警告日志，**不得静默跳过**。
>
> **C5（前缀一致性）**：已确认的写入集合在 WAL 中构成一个**前缀**。即：若 seq = 100 的写入已确认，则 seq = 1..99 的写入必然也已在 WAL 中（或已落入 SST）。不存在「中间挖空一段」的恢复结果。

C5 值得单独强调：它让恢复结果可以用「截断到某个 seq」来描述，而不是「一个任意子集」。这是 `varint64 seq` 单调递增设计的直接收益，也是 `model_check.py` 能用「最终 key 集合」而非「逐条时序」来对拍的前提。

### 2. 实现上必须遵守的三条不变量

这三条是 C1–C5 的充分实现路径，代码评审时逐条对照：

**I1 — ack 必须在 fsync 之后**

```
正确:  写 WAL → fsync(WAL) → 返回 ok
错误:  写 WAL → 返回 ok → 稍后 fsync     ← 崩溃测试可能抓不到，但违约
错误:  写 WAL → fsync(缓冲区指针) → 返回 ok  ← fsync 的不是 WAL fd
```

`cmd/dbcli` 的 `sync:true` 分支必须走 `Db::fsync()`，且**响应字符串的构造与输出都在 fsync 返回之后**。这一条在 `PLAN.md` §6 里被列为「最容易踩的坑」第 2 条。

**I2 — 先写后删**

任何「删除旧文件」的动作，必须发生在「新状态已 fsync 且提交点已切换」之后。具体：

| 动作 | 前置条件 |
|---|---|
| 删旧 WAL | 新 MANIFEST 已 fsync 且 CURRENT 已切换 |
| 删旧 MANIFEST | 新 MANIFEST 已 fsync 且 CURRENT 已切换 |
| 删 compaction 的输入 SST | 输出 SST 已 fsync 且新 MANIFEST 已切换 |
| 删 CURRENT.tmp | `rename` 已成功 |

违反 I2 的典型症状：崩溃后 `CURRENT` 指向的 MANIFEST 引用了已被删除的 SST。

**I3 — 恢复不 panic**

恢复路径上任何一个字节都可能是垃圾。所有解析必须返回 `Result`/`Option`，不得用 `unwrap` 语义（MoonBit 里对应 `panic` 或 `abort`）。坏数据走 `LsmError::Corruption` 并降级到「能恢复多少算多少」。

理由：嵌入式引擎面对的是「用户设备断电」而不是「数据中心有副本」。**能启动的损坏库 > 拒绝启动的完好库**，因为用户至少能把数据导出来。

### 3. 测试分层（明确每层能证明什么）

| 层级 | 手段 | 能证明 | **不能**证明 |
|---|---|---|---|
| L1 | `model_check.py`（同进程，无崩溃） | 功能正确性、C3 | 任何持久化性质 |
| L2 | `crash_test.py`（`kill -9`） | C2 的「整条丢失」、C5、恢复不 panic | **I1（fsync 是否真的调了）** |
| L3 | WAL 尾部截断注入（`--truncate-at`） | I1 的间接证据、C3 的 torn write、C4 | 页缓存丢数据的完整场景 |
| L4 | VM 断电（`virsh destroy`）/ 物理断电 | 全场景，含页缓存丢失 | —（这是唯一完备的手段） |

**当前 v1 交付到 L3。** L4 需要一台能跑 KVM 的机器和自动化脚本，列在 `PLAN.md` Week 3 的 D2 之后，属于「有余力则做」。

**必须在 README 里如实标注**：`kill -9` 测试通过 ≠ fsync 正确。这句话要写进 README 的「崩溃测试」小节，因为绝大多数读者会默认两者等价。

### 4. 崩溃点枚举（测试用例的生成依据）

一次「put 并确认」的完整路径上有 7 个可崩溃位置，恢复后都必须满足 C1–C5：

```
 ①  WAL 帧写到一半            → 截断该帧，put 未生效。若未 ack，符合 C2
 ②  WAL 帧写完，未 fsync      → kill -9 后仍在页缓存，能读到（L2 通过）；断电后消失（L4）
 ③  WAL fsync 完成，未 ack    → 恢复后 put 生效。客户端重试必须幂等（靠 seq 去重）
 ④  ack 已发出                → 必须生效（C1）
 ⑤  memtable 已满，SST 写到一半 → 孤儿 SST，MANIFEST 未引用，启动时清理
 ⑥  SST 写完 fsync，MANIFEST 未切换 → 孤儿 SST，同上
 ⑦  MANIFEST 切换中（CURRENT.tmp 已写，rename 未执行）→ 回退到旧 MANIFEST，旧 WAL 还在
```

位置 ③ 是唯一一个「客户端收到超时但服务端已生效」的场景，因此**所有写操作必须幂等**——这也解释了为什么 `put` 不需要额外的去重逻辑：同 key 同 value 重放的结果相同，`seq` 单调递增保证了后写覆盖先写。

## 后果（Consequences）

### 正面

- 契约可逐条验收：C1–C5 每条都有对应的测试或明确的「当前无法测试」说明。
- 「`kill -9` 不等于 fsync 正确」这个认知被写进文档，避免用错误的测试给自己发合格证。
- I1–I3 三条不变量把「崩溃一致性」这个抽象概念转成了可评审的代码规则。
- 崩溃点枚举直接成为测试用例清单，不用每次重新推导。

### 负面

- **默认 `sync:false` 意味着默认会丢数据。** 需要在 `Options` 文档和 README 里用醒目位置说明，否则用户会误以为「用了 LSM 就自动持久」。
- `sync:true` 每条都 fsync，写吞吐会掉一个数量级（取决于磁盘）。这是物理限制，不是实现问题。benchmark 报告里必须**分开列 `sync:true` 和 `sync:false` 两组数据**，不能只报快的那个。
- L4 未覆盖，意味着「页缓存丢失」场景当前只是设计上正确，没有实测证据。这是已知缺口，不是隐藏缺陷。

### 触发重新评估的条件

1. 引入 group commit（多条写入合并一次 fsync）——会改变 C1 的语义边界，需要新 ADR
2. 引入快照读 / MVCC——需要补充「快照隔离在崩溃后的可见性」契约
3. L4 测试落地——把「设计上正确」升级为「实测通过」，更新本 ADR 的状态

## 备选方案（Alternatives）

### 方案 A：默认 `sync:true`，永不丢数据（否决）

优点：契约最强，用户不用理解 `sync` 参数。
否决理由：每条写入一次 fsync，写吞吐会从「十万级 ops/s」掉到「百级 ops/s」（HDD 上甚至个位数）。这会让引擎在 benchmark 上完全失去竞争力，而 LSM 的核心卖点恰恰是写吞吐。**正确的做法是让用户按场景选，而不是替用户选。**

### 方案 B：不承诺 C5（前缀一致性），只承诺 C1（否决）

优点：实现更自由，WAL 可以乱序刷、可以多线程并发追加。
否决理由：放弃 C5 意味着恢复结果可能是「任意子集」，用户无法用「恢复到某个时间点」来推理，对拍测试也无法用集合比较。这个自由度的收益（并发追加）在当前单线程模型下为零。

### 方案 C：只用 `kill -9` 测试，不引入截断注入（否决）

优点：省掉 L3 的测试代码。
否决理由：这就是本 ADR 背景里说的那个误解。只做 L2 等于给自己发假合格证，而且**恰好漏掉最危险的失效模式**（忘 fsync 在 L2 下完全隐形）。测试的价值在于「能抓到 bug」，一个抓不到目标 bug 的测试是负资产——它会消耗维护成本，还提供虚假信心。

### 方案 D：恢复时遇到任何损坏都拒绝启动（否决）

优点：绝不静默丢数据，语义最干净，符合「fail fast」。
否决理由：与 I3 冲突。嵌入式场景下，用户的数据目录可能因为掉电、文件系统 bug、SD 卡老化而损坏；拒绝启动等于让用户彻底拿不到数据。**降级恢复 + 明确警告**比「干净地拒绝」对用户更有价值。

> 注意这条与 format.md §4.3 的例外并不矛盾：`CURRENT` 缺失时确实拒绝启动，因为那时**没有任何依据**推断数据布局，硬猜必然静默丢数据。而 WAL 尾部截断有明确依据（最后一个完整帧），所以可以降级。区别在于「有没有可信的锚点」。
