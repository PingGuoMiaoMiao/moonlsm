# ADR-0010：给 block 和 filter 加 CRC，格式版本升到 2

- **状态**：已采纳
- **日期**：2026-10-26
- **相关**：ADR-0003（崩溃契约）、ADR-0006（坏 MANIFEST 拒绝启动）、
  `docs/design/format.md` §3.2 / §3.3 / §3.5 / §5.3

---

## 背景

v1 的 SST 只有 footer 的 `magic` 和区域边界检查，data block 内部**没有任何校验**。
这个取舍从 G2 门禁（格式冻结）那天就写在 `format.md` 里，并且当时就把代价量化了：
把一个 173 字节的 SST 逐个位置翻转，**73 个位置被拒绝（42%），58% 被静默接受**。

58% 的静默接受意味着：读出来的值可能是原值，也可能是别的值，而**引擎自己不知道**。
这条被写进了申报书的「已知短板」一栏，作为「v1.1 该先做什么」的证据。

现在是兑现它的时候。但动手之前要把「加在哪、怎么校验、谁来校验」想清楚 ——
加错位置的 CRC 只会带来开销，不会带来安全。

## 决策

**给三类结构各加 4 字节尾部 CRC32C，`version` 从 1 升到 2，读端同时认 1 和 2。**

| 结构 | 尾部 CRC 覆盖范围 |
|---|---|
| data block | entry 区 + restart 数组 + `num_restarts` |
| index block | 同上（index block 就是一个 data block，见 `format.md` §3.4） |
| filter block | `k` + `num_bits` + 位图 |

footer **不加**（理由见「备选方案」）。

校验发生在**打开文件时**，不是读 key 的时候：`open_sst` 解析 index / filter 时校验，
`Db::open` 加载每个 SST 时走一遍 `entries()`（本来就要算 `max_seq`），
任一 block 校验失败即抛 `Corruption` 拒绝启动。

## 三个具体选择

### 1. 为什么 CRC 覆盖结构区，而不只是 entry 区

最省事的做法是「只校验 entry 区」，restart 数组和 `num_restarts` 不管。
问题是 `num_restarts` 本身就是一个**长度字段**：它被改成一个仍然能通过
边界检查的值时，读端会把 entry 区的尾部当 restart 数组读，
得到一个「结构完全合法、内容全错」的 block。这类损坏结构检查永远抓不到。

CRC 的成本与覆盖范围无关（都是线性扫一遍），没有理由留这个洞。

### 2. 为什么 filter 也要 CRC —— 它看起来只是「加速用的」

直觉是：filter 坏了最坏也就是多读几个文件，`may_contain` 保守一点不就行了？
**不行。** filter 的语义是「允许假阳性、禁止假阴性」，位图被改坏时它会返回
`false`，于是引擎理直气壮地回答「没有这个 key」。

这是整个存储栈里**唯一一种会主动丢数据的损坏方向** —— data block 坏了顶多报错，
filter 坏了是「数据明明在，却查不到」，而且查不到的时候没有任何报错。
fuzz 数据也印证了它不是理论风险：加 CRC 之前，filter 区域 80 个位置**全部漏检**，
是整份文件里最大的一块盲区。

### 3. 为什么校验在 open 时，而不是在 get 时

这是本次改动里最不显然的一条，值得写下来。

`Db::get` 的返回类型是 `Bytes?`。它无法表达第三种情况：「这个块我读不懂」。
加 CRC 之前这不算问题，因为 block 解码失败本来就少见；加了 CRC 之后
问题就变成**语义错误**了 —— 明明有校验和能证明「这个块不可信」，
`get` 却只能回答 `None`，也就是「这个 key 不存在」。

用户拿到的是一句谎话，而且是一句听起来完全正常的谎话。

两条路：改 `get` 的签名让它能报错，或者把校验提前到打开时。
选了后者，理由是：

- `Db::open` 本来就要遍历每个 SST 的 `entries()` 来算 `max_seq`，多一次 CRC
  扫描是同一量级的成本，**不引入新的打开开销量级**
- 一旦校验通过，`get` 的返回值就只剩两种含义（有 / 没有），
  API 不需要为「读不懂」留一个位置 —— 而那个位置一旦留出来，
  每个调用方都得处理它，绝大多数调用方会选择忽略
- 损坏在打开时就暴露，比在业务跑到一半时暴露好得多

代价是**打开不是零成本**：一个几 MB 的库，打开时要扫一遍全部 SST 字节。
这是有意的取舍，不是疏忽。

## 备选方案

| 方案 | 否决理由 |
|---|---|
| **整文件一个 CRC** | 只能回答「这个文件坏了」，不能回答「坏在哪一块」。而 LSM 的读路径是按块跳着读的，需要的是块级定位 |
| **每条 entry 一个 CRC** | 一条 entry 30–50 字节，加 4 字节是 10% 的空间开销，换来的是「能定位到条」。块级 CRC 已经能把损坏挡住，没有必要为更细的粒度付这个钱 |
| **只在 `get` 时校验（懒校验）** | 就是上面第 3 条否掉的路：`get` 返回 `Option`，无法表达「读不懂」，只能撒谎说「没有」 |
| **footer 也加 CRC，撑到 52 字节** | 读端定位 footer 靠「从文件末尾倒推 48 字节」。如果 footer 长度随版本变，读端得先知道版本才能算 footer 在哪，而版本本身就在 footer 里 —— 循环依赖。要么读端把 48 和 52 都试一遍，要么接受「可能猜错」。收益（保护 8 字节的 `smallest_seq`）不值得引入这个不确定性 |
| **换 xxHash / BLAKE3** | 这里要的是「发现随机比特翻转」，不是「抗篡改」，CRC32C 完全够用；而且 `crc32c.mbt` 已经在给 WAL 用，复用同一份实现和同一组测试向量（`"123456789" → 0xE3069283`）比多一个哈希函数划算 |
| **只升版本号、不读 v1** | 会炸掉所有已经用 0.2.x 建的库。读到 `version < 当前` 必须能读，这是 `format.md` §5.2 自己定的规则，不能第一次用就破例 |

## 后果

### 正面

- 单字节翻转的检出率从 **42%** 提到 **95.7%**（185 个位置里 177 个被拒绝，
  剩下 8 个全在 footer 的 `smallest_seq` 上）
- filter 的假阴性风险被消除 —— 那原本是唯一一种会主动丢数据的方向
- `format.md` §5.2 的「版本演进规则」第一次真正被执行：写端只写 2，
  读端认 1 和 2，老库不需要迁移工具，下一次 compaction 自然重写成 v2
- 「SST 坏了拒绝启动」这条承诺，现在对**内容损坏**也成立了，而不只是结构损坏

### 负面

- **每块多 4 字节**：data block 目标 4 KiB，空间开销约 **0.1%**
  （每 4 KiB +4 字节）。filter 每个文件多 4 字节，可以忽略
- **打开多一次 CRC 扫描**：`Db::open` 要对每个 SST 的全部字节算一遍 CRC。
  量级上和「本来就要做的 `entries()`」同阶，但它确实是净增的成本
- **两套解码器要长期维护**：`decode_block` / `decode_block_v1`、
  `decode_bloom` / `decode_bloom_v1`。这是向后兼容的固定代价，
  只要还承诺读老库，就得留着
- **v1 老文件读进来仍然不校验**：CRC 是格式自带的，老文件里没有。
  这些文件在下一次 compaction 之前，仍然带着 58% 的盲区
- **footer 的 8 字节仍然是盲区**，而且这次没修（见「备选方案」最后一条）

## 验证方式

- `block_wbtest.mbt`「任意单字节损坏都会被 CRC 拦下」：逐字节改坏，`decode_block` 必须全返回 `None`
- `bloom_wbtest.mbt`「任意单字节损坏都会被 CRC 拦下」：同上
- `sstable_wbtest.mbt`「v1 格式的老文件仍能打开且内容一致」：用 `with_version(SST_VERSION_V1)` 造老文件，逐条比对内容
- `corruption_wbtest.mbt` fuzz：不只断言「有检出」，还把**漏检位置的范围**钉死
  （必须落在 footer 的 `smallest_seq` 区间内）。这样以后谁把某个 CRC 删了，
  这条用例会红，并且直接指出漏在哪
- `moon test` 211 条全绿；native / wasm-gc / js 三后端 `check` 零警告
