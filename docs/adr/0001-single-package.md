# ADR-0001：采用单包多文件，而不是按模块拆包

- **状态**：已接受（Accepted）
- **日期**：2026-10-21
- **决策者**：chendev
- **影响范围**：整个模块布局、所有 `.mbt` 文件的可见性设计

---

## 背景（Context）

LSM 引擎天然分成 9 个左右的模块：`types` / `error` / `bloom` / `block` / `sstable` / `memtable` / `iter` / `wal` / `manifest` / `compaction` / `db`。直觉上应该一个模块一个包，依赖关系清晰、边界分明。

但实际动手时发现三处强耦合，用包边界切开会造成持续的摩擦：

1. **`compaction` 需要同时看到 `memtable` 和 `sstable` 的内部结构。** 合并时要把 memtable 的有序数组和 SST 的 block 迭代器按 key 归并，还要读 `Sst` 的 `first`/`last` key 决定哪些文件重叠。如果 `Sst` 的字段不是 `pub`，compaction 拿不到；如果是 `pub`，那包边界只剩「禁止直接调用私有函数」这一层象征意义。

2. **`db` 需要编排 `wal` / `manifest` / `compaction` 的时序。** 崩溃一致性的核心逻辑就是「谁先写、谁后写、在哪一步 fsync」——这些顺序约束横跨三个模块。包边界不会帮你检查时序，只会让你在写 `wal.append()` 时反复确认它是不是 `pub`。

3. **MoonBit 的 `pub` 是包级导出，没有 `pub(crate)` 这种「模块内可见」的中间档。** 要么全导出，要么完全不导出。这意味着一拆包，本来只想给内部用的 `MemTable::lower_bound` 之类的方法也得 `pub`，对外 API 的边界反而更模糊了。

而 MoonBit 编译器对单包内的**文件顺序不敏感**（不需要像 C 那样前置声明，也不用管 import 环），所以「一个包放 11 个文件」在工具链上没有额外成本。

---

## 决策（Decision）

**v1 采用单包多文件**：所有引擎代码平铺在模块根目录，一个文件一个逻辑模块；只有 `cmd/` 下的可执行入口是独立子包。

依赖方向仍然严格单向（由代码评审和 `PLAN.md` 的表格保证，不由编译器保证）：

```
types / error / bloom
      ↑
   block → sstable
      ↑        ↑
  memtable  manifest
      ↑        ↑
      └── iter ┘
           ↑
          wal
           ↑
      compaction
           ↑
          db
```

对外只暴露 `db.mbt` 里声明的 6 个方法 + `fsync`，其余一律不 `pub`。**API 边界由「不写 `pub`」来守，而不是由包边界来守。**

---

## 后果（Consequences）

### 正面

- 零 import 摩擦，写代码时不用想「这个函数在哪个包」。
- 内部函数可以保持私有，对外 API 反而比拆包时更窄。
- 重构成本低：挪函数、改签名只影响一个包，不会引起一圈 import 报错。
- 编译器能对整包做优化（虽然当前目标是 native，影响有限）。

### 负面

- **依赖方向靠人守，编译器不守。** 可能出现 `types.mbt` 反过来调用 `db.mbt` 的循环依赖，编译器不会报错（同包内互调是合法的）。
  - 缓解：`PLAN.md` 第 2 节列出依赖表，代码评审时对照检查；每个文件顶部写一行注释声明「本文件只依赖 X/Y」。
- 单包编译单元变大，改一个文件要重编整包。当前规模（< 10k 行）下增量编译仍在秒级，可接受。
- 未来若要拆包，需要一次性的搬迁成本。

### 触发重新评估的条件

满足任一条件时，重新开一条 ADR 讨论拆包：

1. 单包超过 **15k 行**，增量编译超过 10 秒
2. 需要发布**多个独立可复用的库**（例如把 `bloom` 单独发布成 `chendev/bloom`）
3. 出现真实的循环依赖，且无法通过抽公共层解决
4. MoonBit 引入 `pub(pkg)` 级别的可见性控制

---

## 备选方案（Alternatives）

### 方案 A：按模块拆成 11 个包（否决）

优点：边界由编译器强制，架构图上每条箭头都有物理对应。
否决理由：上述三处强耦合会让 90% 的跨模块调用都要 `pub`，等于把边界虚化；且 MoonBit 缺少包内可见的中间档，只能全导出或全不导出。

### 方案 B：拆成 3 个包（`core` / `storage` / `db`）（否决）

优点：比 11 个包务实，保留了粗粒度分层。
否决理由：`storage` 里仍然要混 `sstable` / `wal` / `manifest`，与单包相比只多了一层 import，收益不足以抵消搬迁成本。等真的有第二个消费者（比如另做一个 `moonlsm-bench` 模块复用 `block` 编解码）时再拆。

### 方案 C：单包 + 用宏强制依赖检查（否决）

可以写一个构建期脚本扫描 `use` 关系做拓扑排序校验。
否决理由：为一个 10k 行、单人维护的项目引入构建期代码生成，维护成本高于收益。用注释 + 评审表解决即可。
