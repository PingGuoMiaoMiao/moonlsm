# ADR-0008：bloom 的实现方式与文件级 key 区间剪枝

- **状态**：已采纳
- **日期**：2026-10-22
- **相关**：ADR-0007（三层归并）、`docs/engineering/BENCHMARK.md` §5、`bloom.mbt`

---

## 背景

D3 的基准跑出来，100 万条数据的点查延迟是：命中 P50 `0.067 ms`、
**未命中 P50 `0.068 ms`**。

命中与未命中几乎一样慢，这本身是个信号 —— 未命中本该更快，
因为不需要解 block。两个数字一样说明未命中的成本花在了别的地方。

算一下就知道花在哪：100 万条数据在 L2 上约 **77 个 SST**（每个 1 MiB），
而 `Db::get` 是「memtable 未命中 → 依次问每个 SST」。所以一次未命中要：

1. 探 77 个 bloom filter，每个算 **2 遍 FNV-1a**（两个种子各一遍）
2. 每个 filter 做 **7 次 `UInt64` 取模**，共 539 次真除法

`UInt64` 的 `%` 在 x86-64 上编译成 `div`，延迟约 20 个周期。539 次 ≈ 10 800 周期
≈ 3.6 µs，而引擎侧一次点查总共才 10 µs 量级。**三分之一的引擎时间花在取模上。**

同一次测量还暴露了另一件事：范围扫描只有 `32 412 rows/s`。
`scan_range` 已经做了块级剪枝，但仍然对**每个**文件都跑一遍索引二分 ——
而查询区间往往只覆盖极少数文件。

这两件事的共同点是：**在「这个文件里根本没有我要的 key」这件事上，
我们花了远超必要的代价去确认它。**

---

## 决策 1：位图在内存里也按位打包

原来 `BloomFilter` 的位图是 `Array[Bool]`，**一个 bit 占一个字节**。
磁盘上按位打包（§3.3），内存里不打包，靠 `encode` 逐位重排。

代价是 8 倍内存：100 万条数据、10 bit/key、77 个文件，
打包后约 1.25 MiB，不打包是 10 MiB。而且 `encode` / `decode` 都要跑
「每 8 个 bool 一次内层循环」的重排。

改成 `Array[Byte]` 之后：

- 内存与磁盘是**同一份字节**，`encode` 只做整段拷贝，`decode` 也是
- 位图大小降到 1/8
- `popcount` 这类诊断能直接对着内存算

`num_bits` 单独存一份（而不是从 `bits.length() * 8` 推），因为末尾那个字节
可能没用满。`new_with` 里把位数向上取整到 8 的倍数，让这个不一致不会发生；
`decode_bloom` 仍然接受任意 `num_bits`，因为磁盘上可能存在更早版本写的文件。

---

## 决策 2：一次哈希，用 splitmix 终混派生 h2

原来两个种子各跑一遍 FNV-1a：

```moonbit
let h1 = fnv1a(key, 0xCBF29CE484222325UL)
let h2 = fnv1a(key, 0x9E3779B97F4A7C15UL)   // 整条 key 再遍历一遍
```

改成一遍 FNV + 一次 splitmix 终混（6 条整数指令）：

```moonbit
let h = mix64(fnv1a(key, 0xCBF29CE484222325UL))
(h, mix64(h ^ 0x9E3779B97F4A7C15UL))
```

依据是 Kirsch–Mitzenmacher：双哈希 `h1 + i·h2` 只要 `h1`、`h2` 足够独立，
误判率与 k 个独立哈希同阶。实测（`benches/moon/bloom_probe`）10 bit/key、
k=7 时实测 0.830%，理论 0.819%，偏差 1.2% —— 双哈希没有带来可观测的退化。

**`mix64` 不是保险，是必需的。** 这一点踩过坑，见下面「踩到的坑」。

## 决策 3：取模换 fastrange

```moonbit
// 之前
let idx = ((h1 + i * h2) % n).to_int()
// 现在
let idx = (((x & 0xFFFFFFFF) * n) >> 32).to_int()
```

`(u32 * n) >> 32` 等价于 `floor(u32 * n / 2^32)`，把 32 位无符号值均匀映射到
`[0, n)`，只用一次乘法。`n ≤ 2^24`（`decode_bloom` 的上限）时乘积不超过 2^56，
不会溢出。

**分布质量**：不是把值「压缩」到更少的位上，而是把 2^32 个等距区间映射到 n 个桶，
桶大小相差最多 1。实测置位数与理论值的比值 0.9975–0.9988（见 probe 输出），
说明映射没有引入可观测的聚簇。

## 决策 4：先用 key 区间排除文件，再问 bloom

`SstReader` 新增 `range : (Bytes, Bytes)?`，即文件覆盖的闭区间 `[lo, hi]`：

- `hi` = **最后一个 index 条目的 key**（index 存的是每块的 `last_key`）
- `lo` = **首块的第一条 key**（要解一次 block，代价是每个文件一次）

`get` 里先比范围，再问 bloom：

```moonbit
match self.range {
  Some((lo, hi)) =>
    if compare_bytes(key, lo) < 0 || compare_bytes(key, hi) > 0 { return None }
  None => ()
}
```

**为什么放在 bloom 之前**：范围判断是两次 `memcmp`（约 5 ns），bloom 是 7 次
随机位访问（可能 7 次 cache miss）。L2 里的文件按 key 有序且互不重叠，
一次未命中在 77 个文件里有 76 个能被这一步直接排除。

**为什么 `range` 可以是 `None`**：空文件、或首块解码失败时拿不到边界。
这时必须**放行**（不做判断），不能猜。猜错下界的后果是
「数据明明在，却被跳过」—— 这是这个项目里唯一不可接受的错误方向，
比少一个优化严重得多。`sstable_wbtest.mbt` 里有一条用例专门核对
「区间必须真实包住所有 entry，且紧贴首尾两条」。

同一个 `range` 也用在 `scan_range` 开头：区间不相交就返回空，
连索引二分都不做。

## 调参结论：10 bit / 7 哈希 保持不变

`benches/moon/bloom_probe` 是这次加的对照实验工具，跑出来的表：

| bits/key | k | filter 字节 | 实测误判率 | 理论误判率 | 偏差 |
|---:|---:|---:|---:|---:|---:|
| 4 | 3 | 5 004 | 14.632% | 14.689% | 0.996x |
| 6 | 4 | 7 504 | 5.504% | 5.605% | 0.981x |
| 8 | 6 | 10 004 | 2.138% | 2.157% | 0.990x |
| **10** | **7** | **12 504** | **0.830%** | **0.819%** | **1.012x** |
| 12 | 8 | 15 004 | 0.325% | 0.314% | 1.034x |
| 16 | 11 | 20 004 | 0.042% | 0.045% | 0.916x |
| 20 | 14 | 25 004 | 0.006% | 0.006% | 0.894x |

**结论：不改。** 理由不是「10 是经验值」，而是三条一起看：

1. **k=7 已经是最优点**。固定 10 bit 扫 k：k=6 → 0.821%，k=7 → 0.830%，
   k=8 → 0.874%。6 和 7 的差在噪声内，8 开始明显变差。理论最优 k = 10·ln2 = 6.93。
2. **再往上加位，收益递减得很快**。12 bit 把误判率从 0.83% 压到 0.33%，
   但每个文件多 2.5 KB，77 个文件多 190 KB 常驻内存。
   而决策 4 已经把「未命中要探几个文件」从 77 降到 1 ——
   **在只剩 1 个文件可探的情况下，0.83% 和 0.33% 的差别是 0.005 次无效 block 解码。**
3. **往下减位不划算**。8 bit 让误判率翻 2.6 倍，只省 2.5 KB/文件。

换句话说：**参数本身早就是对的，错的是「要探 77 个文件」这件事。**
决策 4 做完之后，bloom 的误判率已经不是瓶颈了。

## 踩到的坑：直接取 FNV 的高 32 位会让分布塌掉

改造过程中我先把探测位置写成 `((x >> 32) * n) >> 32`（取高 32 位做 fastrange），
结果误判率只有理论值的**一半**（10 bit/k=7 实测 0.44%，理论 0.82%）。

看起来像「比理论还好」，实际是分布坏了。诊断方法是加一段 popcount 对照：

```
bits/key=10  num_bits=100000  实际置位=1061  理论置位=9516  比值=0.11
```

**10 000 条 key 只落进了约 1 000 个不同位置。** 根因是 FNV-1a 的雪崩方向：
最后一步是 `(h ^ byte) * prime`，末字节只影响乘数的低 8 位，高位几乎不随它变化。
我的测试 key 又只差末尾几位，于是高 32 位高度相关。

为什么默认配置下看不出来：k=7 时只有 `i=0` 这一个探测用了未混洗的 `h1`，
另外 6 个用的是 `h1 + i·h2`（`h2` 经过 mix64，分布正常）。6 个正常 + 1 个退化，
误判率反而接近正常值 —— **bug 被 k=7 掩盖了**。真正暴露它的是两件事：
把 k 扫到 1（此时唯一的探测就是退化的那个，实测 0.36% 而理论 9.5%），
以及 popcount 诊断。

修法是把 `mix64` 提到 `bloom_hashes` 里，让 `h1` 也经过完整雪崩，并取**低** 32 位。

**教训**：误判率「比理论值低」不是好消息，是要查的信号。
一个只影响部分探测路径的分布问题，会在参数取默认值时自我掩盖 ——
所以调参实验必须把参数扫过整个范围，不能只测默认点。

## 实测效果

同一台机器、同一份 `bench.py`、同一组参数，改动前后各建一个二进制对照跑：

| 指标 | 改动前 | 改动后 | 变化 |
|---|---:|---:|---:|
| 命中 P50 | 0.067 ms | **0.053 ms** | −21% |
| 命中 P95 | 0.110 ms | **0.087 ms** | −21% |
| 命中 P99 | 0.138 ms | **0.111 ms** | −20% |
| 未命中 P50 | 0.068 ms | **0.040 ms** | **−41%** |
| 范围扫描 | 32 412 rows/s | **117 483 rows/s** | **3.6×** |
| 顺序写 | 53 438 ops/s | 55 658 ops/s | +4% |
| 随机写 | 12 708 ops/s | 12 699 ops/s | 0% |
| 空间放大 | 1.13x | 1.13x | 0 |

100 万条数据，`sync=false`，`batch=1000`，`reads=20000`。

未命中的改善（−41%）远大于命中（−21%），符合预期：
命中在找到文件后就停了，而未命中要问遍所有文件 —— 正是决策 4 打击的场景。
扫描的 3.6× 全部来自「区间不相交的文件直接跳过」。

20 万条那组也跑了，命中延迟从 0.064 到 0.067（在 ±10% 噪声内），
未命中 0.053 → 0.047，扫描 69 137 → 104 612。**文件少的时候收益小**，
因为「探 77 个 bloom」这个前提不成立。这从反面印证了归因。

## 遗留问题

1. **`lo` 要解一次 block**。`hi` 是免费的（index 的最后一条），`lo` 不是 ——
   index 只存每块的 `last_key`，拿不到文件的第一条 key。目前是打开文件时
   解一次首块，成本摊到启动。彻底解决要把 `smallest_key` 写进 footer，
   那是磁盘格式变更（需要 bump `SST_VERSION`），留到 v1.1。
2. **`Db::get` 仍是线性遍历文件**。决策 4 把每个文件的判断成本降到两次 `memcmp`，
   但 77 次 `memcmp` 仍是 O(N)。L2 内文件有序且不重叠，理论上可以对文件
   区间做二分，O(log N)。这需要维护「文件按 key 排序」的不变式，
   目前 `self.ssts` 是按 (层号, 编号) 排的，编号与 key 顺序没有保证。
3. **bloom 常驻内存**。每个文件的 filter 在 `open_sst` 时整体解进内存，
   77 个文件约 1.25 MiB。文件数到千级时需要改成 LRU 缓存 filter。
