# ADR-0011：范围扫描改成块级惰性游标

- **状态**：已采纳
- **日期**：2026-10-29
- **相关**：ADR-0008（bloom 布局与文件级剪枝）、`docs/design/API.md` §3.4、
  `sstable.mbt` 的 `SstCursor`、`iter.mbt` 的 `Source`

---

## 背景

`Db::scan(start, end, limit)` 从实现的第一天起就是这样的：

```moonbit
let sources : Array[Array[Entry]] = []
sources.push(self.mem.to_entries())
for s in self.ssts {
  sources.push(s.reader.scan_range(start, end))   // 整个区间，全解出来
}
let it = MergeIterator::new(sources)
while out.length() < limit { ... }                // 到这才开始截断
```

`limit` 只作用在**归并之后**。所以「取前 10 条」和「取全部 10 万条」付同样的解码成本：
每个 SST 都要把 `[start, end)` 覆盖的每一块解出来、每条 entry 建一个对象、
塞进数组，然后归并器只读了前 10 条就把剩下的丢掉。

`BENCHMARK.md` §4 从 10-25 起就写着「剩下的差距来自架构：不是流式迭代器」，
一直挂着没动，因为它是**改动面最大**的一项（读路径、归并器、compaction 都要碰）。

量一下它到底值多少。50 万条、46 个文件、`levels=[2, 0, 44]`：

| 查询 | 旧路径 | 说明 |
|---|---:|---|
| `scan("key", "kez", limit=10)` | **572 ms** | 前缀扫描第一页，扫全库只取 10 条 |
| `scan("key", "kez", limit=1000)` | 512 ms | 同上，limit 放大 100 倍 |
| `scan(key…0000, key…0500, 500)` | 2.02 ms | 区间本身就只有 500 条 |

第一行是最常见的查询形状（前缀分页），也是最荒谬的一行：**用户要 10 条，
引擎解了 50 万条。**

## 决策

**把「来源」抽象成可惰性推进的游标，归并器按需拉取；`limit` 一到就停。**

三处改动：

1. **`SstCursor`**（`sstable.mbt`）：持有 `SstReader` + 索引 + 当前块 + 块内位置。
   `peek()` 返回当前条目，块用完才 `load_next()` 解下一块。区间过滤在解块时做。
2. **`Source` 枚举**（`iter.mbt`）：`FromArray(ArrayCursor)` 与 `FromSst(SstCursor)`。
   归并器只认 `peek` / `advance` / `failed` 三个操作，不关心来源是内存还是磁盘。
3. **文件级剪枝前置**（`db.mbt`）：`overlaps(start, end)` 为假的文件**根本不进**归并器。

## 三个具体选择

### 一、为什么不是「给 `scan_range` 加个 `limit` 参数」

这是最省事的想法，也是错的。单看一个文件，无法判断「前 N 条」是不是**全局**的前 N 条 ——
多路归并要求跨文件比较。给文件 A 取 10 条、给文件 B 取 10 条，归并后可能只剩 3 条
（其余被更新的版本覆盖），也可能本该有 10 条来自 A 的第 11 条。

所以限制**只能**在归并层施加。而限制一旦在归并层，来源就必须能被「取一条、再取一条」
地推进 —— 这就是游标。

### 二、为什么归并器不抛错

`SstCursor::load_next` 里解码块可能失败（`decode_block` 返回 `None`、`entries()` 抛 corruption）。
最直觉的做法是让 `peek` 也 `raise LsmError`，然后 `MergeIterator::next` 跟着 `raise`。

代价：`next` 的签名一改，compaction 的调用点、`iter_wbtest.mbt` 的 8 处构造全要改，
而且归并器从「纯函数」变成「会失败的东西」——它本来只做数据变换，不该关心 IO。

所以改成**记标志**：`SstCursor.failed`、`MergeIterator::failed()`，
由 `Db::scan` 在返回前检查，有失败就 `raise Corruption`。

**这不是「静默忽略错误」**：出错的那个来源会静默变成空，结果就少了那部分数据，
所以必须检查。检查放在 `Db::scan` 是因为那是唯一知道「这次扫描该返回什么」的地方。

顺带说明为什么这条路径正常走不到：`Db::open` 已经把每个 SST 的 `entries()` 全解过一遍
（ADR-0010 加的校验），而 `SstReader.data` 是打开时的内存副本，之后不会被改。
运行期解码失败意味着**内存被人动了**，那本来就不是这个库能兜住的事。

### 三、为什么文件级剪枝要前置到归并器之外

`SstCursor` 内部已经做了「整个文件与区间不相交就直接空游标」，看起来够用了。
不够 —— 归并器每取一行都要遍历**所有**来源：

```moonbit
for i in 0..<self.sources.length() { ... self.sources[i].peek() ... }
```

一个永远返回 `None` 的来源，也照样要付一次 `peek` 的钱（enum match + 方法调用）。
55 个文件里只有 1 个可能相交时，另外 54 个就是纯粹的乘数，乘在每一行上。

这一条是实测出来的，不是想出来的：第一版把 55 个来源全塞进归并器，
「中段 500 条」从 2.53 ms **退化到** 11.53 ms（慢 4.5 倍）。
剪枝前置之后回到 2.02–3.11 ms，与旧路径持平。

## 数据

同场 A/B（`benches/python/scan_ab.py`），50 万条、46 个文件、`levels=[2, 0, 44]`，
同一份数据的两个独立副本，15 轮 ABBA 交替取中位数：

| 场景 | 返回条数 | 旧路径 (ms) | 新路径 (ms) | 加速 |
|---|---:|---:|---:|---:|
| 前缀扫描取前 10 | 10 | 572.29 | **10.67** | **53.6×** |
| 前缀扫描取前 1000 | 1000 | 512.37 | **14.06** | **36.4×** |
| 中段 500 条 | 500 | 2.02 | 2.17 | 0.93× |
| 中段 10 条 | 10 | 0.29 | 0.27 | 1.06× |

两个「中段」场景在多次重测里落在 0.93×–1.18× 之间，**是噪声，不是收益也不是回归**。
原因清楚：区间窄的时候块级剪枝（ADR-0008）已经把旧路径限制在 2–3 个块上，
新路径要解同样多的块，唯一区别是 `peek` 比数组下标慢一点。

**这个 trade-off 是真实的，不打算掩盖**：新路径把「per-row 的常数」换成了
「按需解块」。宽区间小 limit 赢几十倍，窄区间可能输几个百分点。

端到端（`bench.py`，20 万条，随机区间 500 条，100 次）：
**61 611 → 101 915 rows/s**。这组**不是**同场 A/B（两次独立运行），
只作为量级参考；严谨的数字看上面那张表。

## 备选方案

| 方案 | 否决原因 |
|---|---|
| 给 `scan_range` 加 `limit` | 单文件看不到全局前 N 条，见「选择一」 |
| 归并器改成堆（`BinaryHeap`） | k 通常是个位数，堆的收益不抵一层复杂度；真正的瓶颈是解码量，不是比较次数 |
| 只在 `Db::scan` 里「先取 10×limit 再截断」 | 启发式：可能不够（大量墓碑/旧版本），也可能浪费（limit 很大时白取）。而且它不解决「解了整个区间」的问题，只是把 10 万条变成 100 条 |
| `Source` 用 trait 而不是枚举 | 只有两个实现，枚举的 match 比动态分派快，也不需要 `&dyn` 的装箱 |
| 让 `peek` 抛错，归并器跟着 `raise` | 波及 compaction 与全部归并测试，且把 IO 错误塞进纯数据变换，见「选择二」 |

## 后果

**好的：**

- 前缀分页（最常见的查询形状）从「扫全库」变成「解几块」，50 倍量级
- `limit` 第一次真正生效 —— 之前它只是个「截断」参数
- 归并器不再假设「来源已经在内存里」，为将来「SST 不整体加载」留了口子
- `Db::scan` 的「返回恰好字典序前 limit 条」这个语义，现在有实现支撑了
  （`API.md` §3.4 的待定项可以落定）

**代价：**

- 读路径多了一层间接：`peek`/`advance` 代替数组下标。窄区间时可能慢几个百分点（噪声内）
- `SstCursor` 有 6 个可变字段，状态机比「一次返回数组」难读。`sstable_wbtest.mbt`
  里 4 条测试专门钉它：惰性（`block_i` 断言）、与 `scan_range` 逐条一致、
  重复 `peek` 幂等、空文件立刻耗尽
- `scan_range` 保留不删：它是游标的对照基准（「新实现必须与老实现逐条一致」），
  也是 compaction 之外唯一还在用「整段返回」的地方

**没变的：**

- 磁盘格式一个字节没动
- `Db::scan` 的签名、语义、左闭右开约定
- 墓碑仍然在 `Db::scan` 里被吃掉（游标层不处理墓碑 —— 它不知道上面还有没有更新版本）

## 验证方式

```bash
moon test                                    # 215 条，含 4 条游标专项
moon test --target wasm-gc .                 # 190 条
python benches/python/scan_ab.py --old ... --new ...
```

游标的 4 条测试里，**「取 3 条只解 1 块」是核心**：它断言 `block_i == 1`。
只测「结果对不对」不够 —— 一个「先全解再截断」的实现结果同样正确，
但它没省下任何解码成本。这条断言把「惰性」从意图变成约束。

「与 `scan_range` 逐条一致」用**旧实现当基准**，覆盖 9 种区间（全区间、两端落在块中间、
极窄、空区间、start > end、贴尾部、覆盖全部、两个完全在区间外的方向）。
手写期望值只会覆盖想得到的情况。

## 一条方法论更正

同场 A/B 必须用 **ABBA** 交替，不能固定「先旧后新」。

固定顺序会系统性偏袒先跑的那个（它总拿到「上一个请求刚把页缓存焐热」的位置）。
实测过：两边代码**完全一样**的写路径，固定顺序稳定测出 15% 的差异；
换成 ABBA 后差异消失（0.966，min/max 区间重叠）。

`scan_ab.py` 因此按 `r % 2` 翻转顺序。ADR-0009 那次的 6.3× 不受影响（量级差太远），
但以后所有 A/B 都该这样写。
