# ADR-0007：归并采用三层、整层下沉，墓碑只在最底层丢弃

- **状态**：已采纳（推翻了 `compact.mbt` 早期注释里「v1 不丢墓碑」的说法）
- **日期**：2026-10-21
- **相关**：ADR-0003（崩溃一致性契约）、ADR-0005（组提交）、`docs/design/format.md` §4

---

## 背景

`flush` 每刷一次就往 L0 加一个 SST，而 L0 的文件之间**范围可以重叠**
（它们来自不同时刻的 memtable）。于是读一个 key 要依次问遍所有 L0 文件，
读放大是 O(文件数)，而文件数只增不减。

D5 先做了最小可用的版本：L0 → L1 一层归并，且**不丢弃墓碑**。
当时的理由写在 `compact.mbt` 的注释里：

> 墓碑遮蔽「更下层里的旧值」，只要还存在更低层就必须留着。
> 丢弃墓碑需要额外证明「这个 key 在 L1 里没有更旧的版本」，
> 而只要漏掉一个分支就会让删掉的数据复活。留到 D6 单独做。

D6 就是来做这件事的。做的过程中有三个决策需要记录。

---

## 决策 1：从两层改成三层

最初的设计是 `L0 + L1`，L1 就是最底层。

这个设计有个隐蔽的问题：**「墓碑能不能丢」的判定退化成恒真**。
如果只有两层，那么每次归并的目标层都是最底层，`is_bottom_level(dst)`
永远返回 `true`，那个分支永远不会被证伪 —— 而它恰恰是最危险的分支
（判错的后果是「删掉的数据复活」，比「数据没删掉」严重得多）。

于是加了 L2：

```
L0（memtable 刷出来的，可重叠）  --个数 >= 4-->       L1
L1（不重叠）                     --字节 >= 1 MiB-->  L2
L2（不重叠，最底层，不再下沉）
```

这样「写进 L1」和「写进 L2」是两条都会真实走到的路径，
`is_bottom_level` 是一个有真假两态的判定，测试里两条都能断言到。
代价是多了 `LEVEL_FANOUT = 10` 这一层写放大（每份数据从 L1 走到最底层
大约被重写一次），在 v1 规模下可以接受。

`LEVEL1_TARGET_BYTES` 取 1 MiB 是刻意选小的：小到让 L1 → L2 在测试里
真的会发生（否则那条路径永远只有代码没有验证），大到不会每次 flush 都触发。

## 决策 2：每层取**整层**下沉，而不是取一个文件

标准 Leveled Compaction 是「从 L_src 取一个文件 + L_src+1 里与之重叠的文件」。

v1 取的是**整层**。理由：

- L0 的文件互相重叠，取一部分没有意义（剩下的还得再归并一次）。
- L1 及以下的整层上限就是 `level_target_bytes`（1 MiB），整层下沉的
  写放大是 O(1 MiB)，不会失控。
- 「取一个文件」需要决定「取哪个」（最旧？轮转？最左？），每种选择都
  引入新的状态和新的测试面，而收益（把 1 MiB 的写放大降到 100 KiB）
  在 v1 的规模下看不出来。

代价写在这里，免得以后有人以为这是疏忽：

> **L1 → L2 每次都会重写整个 L1，以及 L2 里与 L1 范围重叠的全部文件。**
> 当 L2 长到 10 MiB 而 L1 的 key 范围又很宽时，一次下沉要重写 10 MiB。
> 等有 benchmark 能测出这个代价时再改成「取一个文件」。

代码里 `new_upper` 因此直接是空数组，并且注释写明了：若将来改成
只取一个文件，`sources` / `inputs` / `new_upper` 三处必须一起改 ——
否则会出现「文件还在 `version` 里，但内存视图里没了」这种最难查的状态。

## 决策 3：墓碑只在写进最底层时丢弃

### 规则

```moonbit
let drop_tombstones = is_bottom_level(dst)
```

### 为什么这样是安全的

设本次归并把 `src` 层的**全部**文件与 `dst` 层中与 `src` 范围重叠的
**全部**文件作为输入，输出写进 `dst`。

对任意一个在输入里出现过墓碑的 key `k`：

1. `k` 落在 `src` 层的某个文件里，因此 `k ∈ [lo, hi]`（`src` 层的 key 范围）。
2. 若 `dst` 层存在包含 `k` 的文件，该文件的范围必然与 `[lo, hi]` 相交
   （因为 `k` 同时落在两个区间里），所以它在**输入**里。
3. `dst` 是**最底层**，`k` 的更旧版本不可能存在于更下面。
4. 归并按 `seq` 取最大，所以 `k` 在输入里的所有旧版本都被淘汰，
   只剩墓碑本身。
5. 墓碑的作用是遮蔽旧值。旧值已经不存在了，墓碑没有东西可遮。

所以丢弃它是安全的。

第 2 步是关键，也是「范围重叠」判定必须严格的原因：如果把
`m.largest == lo` 这种首尾相接误判成重叠、或者漏判成不重叠，
第 2 步就不成立，旧值会活下来。

第 3 步是为什么必须检查 `is_bottom_level`：如果 `dst` 不是最底层，
`k` 的旧版本可能躺在 `dst + 1`，那块墓碑就得留着。

### 反过来：写进非最底层时必须留着

`compact_wbtest.mbt` 里有一条用例专门守这个：

```
compact: 墓碑写进非最底层时必须留着，能压住更下层的旧值
```

它断言 L0 → L1 之后 `count_entries(gone) == 1`。如果哪天有人
「顺手」把 `drop_tombstones` 改成恒 `true`，这条会立刻红。

### 全部都是墓碑的情况

如果一次归并的输入全是墓碑（那批 key 全被删了），`merged` 会是空数组。

**不能提前 `return`。** 提前返回会让这批墓碑永远留在 L0 里，
每次 flush 都重试一遍归并 —— 而且 L0 永远清不空，写放大无限增长。

正确做法是照常走完后面几步：不产出任何文件，但把 `src` 清空、
把 `dst` 里参与的文件移除、`persist_version()`、删掉输入文件。
数据就真的没了。

## 崩溃安全性

和 D5 一样，七个步骤，原子点在 `persist_version()`：

```
1. 算 src 层范围 + 找 dst 层重叠文件
2. 读入全部输入 → 归并 → 到最底层时丢墓碑
3. 按大小切成若干 SST，逐个写盘 + fsync
4. 更新 version
5. persist_version()   ← 原子点
6. 删除输入文件
7. 重建内存视图
```

- **5 之前崩溃**：CURRENT 仍指旧 MANIFEST，输入文件都还在 → 数据完好；
  新写的 SST 是孤儿，`bump_file_number_past_existing` 会跳过它们的编号。
- **5 之后崩溃**：新 MANIFEST 只引用新文件，输入文件成了垃圾，
  但不影响恢复。

**第 6 步必须在第 5 步之后。** 提前删输入文件的话，一旦 5 失败，
旧 MANIFEST 引用的文件已经没了 —— 数据库直接打不开。

---

## 内存视图的重建方式改了

D5 是手工拼的：`kept = 老文件里没被吃掉的` + `新文件追加在后面`。

这在 v1 下**碰巧**是对的（新输出与幸存的 L1 文件范围不相交，
两种顺序结果一样），但那是「归并只碰重叠文件」的副产品，不是保证。
一旦将来放宽重叠判定，`get` 就会静默读到旧值 —— 因为 `get` 靠
`self.ssts[0]` 是最新的文件来做短路（命中第一个就返回，**不比较 seq**）。

现在改成 `reload_sst_view`：按 `version` 重排一遍，
「层号升序 + 层内编号降序」，与 `recover()` 的加载顺序**同一套规则**。
唯一的事实来源是 `version` 本身，不再靠人工推理「谁该在前面」。

## 遗留问题

1. **没有后台线程。** `maybe_compact` 在 `flush` 末尾同步执行，
   一次 flush 可能连带两次归并。v1 没有并发控制，后台 compaction
   会和写入抢同一个 `version`，引入的锁比它能省下的延迟更值得担心。
2. **孤儿 SST 没有回收。** 崩溃在「写完 SST」和「写 MANIFEST」之间会
   留下没人引用的文件，只是不再分配那个编号。需要一个启动时的
   「扫一遍 `sst/`，删掉 `version` 里没有的」步骤。
3. **墓碑丢弃只在最底层做，但最底层会被反复重写。** 已删除的 key 在
   最底层被物理清掉之后，如果它在上层又有新写入，会重新走一遍
   「写 → 删 → 下沉」。这是 LSM 的固有行为，不是 bug。
4. **`contains_meta` 是线性扫描。** 一个层几十个文件时没问题；
   等改成「取一个文件」并且层里出现几千个文件时要换成 `Map`。
