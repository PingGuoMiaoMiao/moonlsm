# 性能基准

**测量环境**：Windows 11，NTFS，`moon build --target native --release`。
所有数字都是本机实测，没有挑选，包括不好看的那些。

复现：

```bash
moon build --target native --release
cd benches/python

# 主表：100 万条
python bench.py --cmd "../../_build/native/release/build/cmd/dbcli/dbcli.exe" \
  --n 1000000 --reads 20000

# 持久化路径（每批一次 fsync）
python bench.py --cmd "../../_build/native/release/build/cmd/dbcli/dbcli.exe" \
  --n 200000 --reads 20000 --sync

# 参照：SQLite（同 workload）
python bench_sqlite.py --n 200000 --reads 20000

# bloom 的误判率对照（不经过 CLI，直接测 filter）
cd ../..
moon run benches/moon/bloom_probe --target native
```

## 1. 主表

### moonlsm · 100 万条 · 每批 1000 条 · value 100 字节

| 指标 | 数值 |
|---|---|
| 顺序写吞吐 | **55 658 ops/s**（6.40 MB/s） |
| 随机写吞吐（覆盖写） | **12 699 ops/s**（1.46 MB/s） |
| 读延迟 P50（命中） | **0.053 ms** |
| 读延迟 P95 | 0.087 ms |
| 读延迟 P99 | 0.111 ms |
| 读延迟 P50（未命中） | 0.040 ms |
| 范围扫描（每次 500 行） | **117 483 rows/s** |
| 磁盘占用 | 144.1 MB |
| 逻辑数据量 | 127.0 MB |
| 空间放大 | **1.13×** |

### moonlsm · 20 万条（对照，含两种写入模式）

| 指标 | `sync:false` | `sync:true` |
|---|---|---|
| 顺序写 | 47 791 ops/s | 34 054 ops/s |
| 随机写 | 29 818 ops/s | 23 859 ops/s |
| 读 P50 / P95 / P99 | 0.067 / 0.097 / 0.117 ms | 0.049 / 0.082 / 0.102 ms |
| 读 P50（未命中） | 0.047 ms | 0.035 ms |
| 范围扫描 | 104 612 rows/s | 115 926 rows/s |
| 空间放大 | 1.83× | 1.83× |

**`sync:true` 的代价是 1.40×（47 791 → 34 054），不是数量级。** 一批 1000 条只
fsync 一次，200 批就是 200 次 fsync —— 摊到 20 万条上可以忽略。详见 ADR-0005。

> **这些数字和上一版文档里的不一样，原因见 §5 第 3 条。** 本表整组是
> 2026-10-22 同一场测量里跑出来的；上一版记录的 `50 806 / 46 316`（1.09×）
> 是更早一场测的。同一台机器、同一份代码，隔一天再测，顺序写吞吐能差 30%。
> 所以本文件里**任何跨会话的对比都不成立**，只有同一场里的 A/B 才可信。

### ADR-0008 改动前后的对照（同一场 A/B，100 万条）

为了不拿「几天前的数字」当基线，这里用 `git worktree` 把改动前的提交单独
建了一份二进制，两个二进制在同一场里背靠背跑同一个 `bench.py`：

| 指标 | 改动前 | 改动后 | 变化 |
|---|---:|---:|---:|
| 命中 P50 | 0.067 ms | **0.053 ms** | −21% |
| 命中 P95 | 0.110 ms | **0.087 ms** | −21% |
| 命中 P99 | 0.138 ms | **0.111 ms** | −20% |
| 未命中 P50 | 0.068 ms | **0.040 ms** | **−41%** |
| 范围扫描 | 32 412 rows/s | **117 483 rows/s** | **3.6×** |
| 顺序写 | 53 438 ops/s | 55 658 ops/s | +4%（噪声内） |
| 随机写 | 12 708 ops/s | 12 699 ops/s | 0% |
| 空间放大 | 1.13× | 1.13× | 0 |

未命中的改善（−41%）远大于命中（−21%），符合归因：命中在找到文件后就停了，
未命中要问遍所有文件 —— 正是「文件级 key 区间剪枝」打击的场景。

20 万条那组也跑了：命中 `0.064 → 0.067`（噪声内）、未命中 `0.053 → 0.047`、
扫描 `69 137 → 104 612`。**文件少的时候收益小**，因为「一次未命中要探 77 个
bloom」这个前提不成立。这从反面印证了归因，不是「顺手改了什么就都变快了」。

细节见 [ADR-0008](../adr/0008-bloom-layout-and-file-range-pruning.md)。

## 2. 组提交到底省了多少

同样的工作量，把批次改成 1（每条写都要等 fsync）：

| 实现 | 每条一次 fsync | 不等 fsync | 倍数 |
|---|---|---|---|
| moonlsm 顺序写 | 76 ops/s | 2 995 ops/s | **39×** |
| moonlsm 随机写 | 104 ops/s | 10 607 ops/s | **102×** |
| SQLite 顺序写 | 498 ops/s | 31 136 ops/s | 63× |
| SQLite 随机写 | 766 ops/s | 44 767 ops/s | 58× |

（`--n 2000 --batch 1`，两边都是单条提交。）

结论有两条：

1. **「持久化很慢」主要是 fsync 的物理成本，不是实现问题。** 连 SQLite
   在 `synchronous=FULL` 下也只有 498 ops/s。
2. **组提交把 39× 的代价压到 1.40×**（47 791 → 34 054）。
   这就是 `putmany` 存在的唯一理由。

**但单条 `put` 仍然慢**：76 ops/s = 13.2 ms/条，而 SQLite 是 2.0 ms/条。
差 6.6 倍的原因已经定位过（ADR-0005）：Windows 上每次 `fopen`/`fclose`
约 5.9 ms，且与写入字节数无关，而 `put` 每条都要开关一次文件。
修法是让 `NativeStorage` 缓存 WAL 的文件句柄 —— 属于 v1.1，见「已知问题」。

> 这里曾有 76 与 79 两个数并存：79 是更早一轮的测量，表里 76 是后一轮。
> 两个都在 ±5% 噪声内，统一取表里的 76（也是申报书引用的那个），
> 免得读者以为两组数据打架。

## 3. 与 SQLite 的对照

**这不是竞品对比。** SQLite 是成熟二十多年的 C 实现；moonlsm 是教学级 LSM。
拿绝对数字分高下没有意义，这里只是给「50k ops/s 算快还是慢」一个锚点。

### 20 万条 · 每批 1000 条 · 都不同步 fsync

| 指标 | moonlsm | SQLite | 倍数 |
|---|---|---|---|
| 顺序写 | 47 791 ops/s | 404 900 ops/s | 8.5× |
| 随机写 | 29 818 ops/s | 23 311 ops/s | **0.78×（moonlsm 更快）** |
| 读 P50（命中） | 0.067 ms | 0.010 ms | 6.7× |
| 读 P50（未命中） | 0.047 ms | 0.004 ms | 12× |
| 范围扫描 | 104 612 rows/s | 1 884 737 rows/s | 18× |
| 空间放大 | 1.83× | 1.20× | — |

> **为什么这张表写 0.067，主表却写 0.053？** 两个数不同场：本表是 20 万条，
> 主表是 100 万条，中间隔了几天。本文档自己承认跨会话能差 20–26%，
> 而 0.067 / 0.053 = 1.26 正好落在这个量级里 —— 不是两套口径打架。
> 要下结论只能用同场对照（ADR-0008 那张 A/B 表就是这么来的），
> 跨表相减得出的「引擎自身 0.02 ms」只能当量级看，不能当结论。

**这张表有一处对 moonlsm 严重不利，必须先说清楚**：SQLite 在同一个 Python
进程里跑，moonlsm 走「子进程 + 一行 JSON 一条命令」的协议。每读一次都要
一次管道往返 + 一次 JSON 解析。

用「未命中读」可以估出这个协议地板：bloom + 文件区间判断直接否定，引擎侧
几乎不做任何工作，**0.047 ms 基本就是一次往返的成本**。命中读是 0.067 ms，
也就是说**引擎自身的点查大约 0.02 ms，与 SQLite 的 0.010 ms 同数量级**
（差 2 倍，不是 6.7 倍）。

范围扫描的 18 倍差距没这么乐观：即使扣掉协议开销，仍然差一个数量级。
原因在 `Db::scan` 的架构 —— 见下节。

**随机写比 SQLite 快，不用当成成就。** 两者语义不同：moonlsm 的覆盖写
只是往 memtable 里插一条带新 seq 的记录（旧值留在 SST 里等归并），
SQLite 要原地更新页并维护 B-tree。代价体现在空间放大（1.83× vs 1.20×）。

## 4. 已知瓶颈

### 范围扫描（优化过两轮，仍是最大短板）

第一次跑出来的数字是 **1 250 rows/s**（扫 500 行要 400 ms）。三个原因：

1. **`Db::scan` 对每个 SST 调 `entries()`**，把整个文件解出来再筛。
   改成 `SstReader::scan_range`：用索引做块级剪枝，只解落在区间里的块。
2. **CLI 的 JSON 拼装是 `body = body + ...`**，O(n²) 拷贝。
   500 条 × 115 字节要拷十几 MB。改用 `Buffer`。
3. **`esc` 逐字符拼接**，115 字符的 value 要拷 6.5 KB。
   加了「先扫一遍确认无需转义就直接返回原串」的快路径。

第一轮 **1 250 → 58 834 rows/s（47×）**。

第二轮（ADR-0008）发现块级剪枝还漏了一步：剪的是**块**，但没剪**文件**。
查询区间往往只覆盖一两个文件，而每个文件都要跑一遍索引二分。
加了文件级 key 区间判断之后 **32 412 → 117 483 rows/s（3.6×）**
（100 万条那组，同一场 A/B）。

剩下的差距来自架构：`Db::scan` 仍然是「把每个来源的区间条目全读进数组，
再 k 路归并」，不是流式迭代器。要做到 SQLite 那个量级，
需要 `Block` 级别的惰性游标 —— v1 不做。

### 空间放大 1.83×（20 万条）

三个来源：L0 与 L1 的重叠、墓碑（v1 只在最底层丢弃）、以及每次归并都
整层重写。100 万条时降到 1.13×，因为数据基本都沉到了 L2，重叠少了。

### 单条持久化写 76 ops/s

见第 2 节。根因是每次写都 `fopen`/`fclose` 一次 WAL。
同一场里 SQLite 是 498 ops/s，差 6.5 倍 —— 全在文件开关上。

### 顺序写不如随机写（20 万条那组）

`29 818` vs `47 791` —— 随机写比顺序写慢 38%，这是**正常**的：随机写那轮
是覆盖写，每个 key 都要在 memtable 的有序数组里二分插入并 memmove。
但 100 万条那组是 `12 699` vs `55 658`，差距拉大到 4.4 倍，
说明数据量上去之后覆盖写触发的归并更多。

### bloom filter 常驻内存（新记，未处理）

每个 SST 的 filter 在打开时整体解进内存。100 万条数据 77 个文件约 1.25 MiB
（10 bit/key）。文件数到千级时需要改成 LRU 缓存 —— v1.1。

## 5. 测量方法的局限（必须一起看）

1. **协议开销吃掉了小操作的绝大部分。** 所有读延迟数字都包含一次管道往返。
   引擎真实延迟要比表里的小。
2. **`kill -9` 测不出「忘了 fsync」**（ADR-0003）。`sync:false` 那几组数字
   不代表持久化能力，它们代表「引擎本身的吞吐上限」。
3. **单机单次测量，没有取多轮中位数。** 同一场里同一条命令跑三次，
   吞吐波动约 ±10%。更麻烦的是**跨会话的漂移**：同样的代码，隔一天再测，
   20 万条顺序写从 50 806 掉到 47 791（−6%），`sync:true` 那组从 46 316
   掉到 34 054（−26%）。原因没有定位（怀疑是机器负载或磁盘缓存状态），
   但这意味着**拿几天前记录的数字当基线是错的**。
   所以 ADR-0008 的对照改用 `git worktree` 建两份二进制、在同一场里背靠背跑 ——
   只有这种 A/B 的差值可以信，绝对值只能看量级。
4. **没有和 moonkv 对比。** 计划里有，尚未做。
5. **Windows 的文件系统开销明显高于 Linux**（`fopen` 5.9 ms 这个数字就是
   Windows 特有的）。同样的代码在 Linux 上单条 fsync 会快很多，
   这里没有条件实测，所以不写推测的数字。
6. **bloom 的误判率是单独测的，不是端到端测的。** 误判率用
   `moon run benches/moon/bloom_probe --target native` 直接对 filter 测
   （100 万次查询，确定性结果）；端到端延迟里那一部分没法单独拆出来。
   两者能对上是因为「文件级区间剪枝」之后未命中只剩 1 个文件可探 ——
   如果哪天这个前提变了，误判率需要重新评估。
