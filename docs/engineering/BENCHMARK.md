# 性能基准

**测量环境**：Windows 11，NTFS，`moon build --target native --release`。
所有数字都是本机实测，没有挑选，包括不好看的那些。

复现：

```bash
moon build --target native --release
cd benches/python

# 主表：100 万条
python bench.py --cmd "../../_build/native/release/build/cmd/dbcli/dbcli.exe" \
  --n 1000000 --reads 20000

# 持久化路径（每批一次 fsync）
python bench.py --cmd "../../_build/native/release/build/cmd/dbcli/dbcli.exe" \
  --n 200000 --reads 20000 --sync

# 参照：SQLite（同 workload）
python bench_sqlite.py --n 200000 --reads 20000
```

## 1. 主表

### moonlsm · 100 万条 · 每批 1000 条 · value 100 字节

| 指标 | 数值 |
|---|---|
| 顺序写吞吐 | **50 212 ops/s**（5.77 MB/s） |
| 随机写吞吐（覆盖写） | **12 724 ops/s**（1.46 MB/s） |
| 读延迟 P50（命中） | **0.068 ms** |
| 读延迟 P95 | 0.113 ms |
| 读延迟 P99 | 0.147 ms |
| 读延迟 P50（未命中） | 0.067 ms |
| 范围扫描（每次 500 行） | **32 895 rows/s** |
| 磁盘占用 | 144.1 MB |
| 逻辑数据量 | 127.0 MB |
| 空间放大 | **1.13×** |

### moonlsm · 20 万条（对照，含两种写入模式）

| 指标 | `sync:false` | `sync:true` |
|---|---|---|
| 顺序写 | 50 806 ops/s | 46 316 ops/s |
| 随机写 | 23 457 ops/s | 25 730 ops/s |
| 读 P50 / P95 / P99 | 0.060 / 0.096 / 0.120 ms | 0.052 / 0.085 / 0.104 ms |
| 读 P50（未命中） | 0.053 ms | 0.042 ms |
| 范围扫描 | 58 834 rows/s | 80 025 rows/s |
| 空间放大 | 1.83× | 1.83× |

**`sync:true` 几乎不掉速，这是组提交的效果。** 一批 1000 条只 fsync 一次，
200 批就是 200 次 fsync —— 摊到 20 万条上可以忽略。详见 ADR-0005。

## 2. 组提交到底省了多少

同样的工作量，把批次改成 1（每条写都要等 fsync）：

| 实现 | 每条一次 fsync | 不等 fsync | 倍数 |
|---|---|---|---|
| moonlsm 顺序写 | 79 ops/s | 3 103 ops/s | **39×** |
| moonlsm 随机写 | 109 ops/s | 11 867 ops/s | **109×** |
| SQLite 顺序写 | 497 ops/s | 34 426 ops/s | 69× |
| SQLite 随机写 | 763 ops/s | 44 897 ops/s | 59× |

结论有两条：

1. **「持久化很慢」主要是 fsync 的物理成本，不是实现问题。** 连 SQLite
   在 `synchronous=FULL` 下也只有 497 ops/s。
2. **组提交把 39× 的代价压到 1.09×**（50 806 → 46 316）。
   这就是 `putmany` 存在的唯一理由。

**但单条 `put` 仍然慢**：79 ops/s = 12.6 ms/条，而 SQLite 是 2.0 ms/条。
差 6 倍的原因已经定位过（ADR-0005）：Windows 上每次 `fopen`/`fclose`
约 5.9 ms，且与写入字节数无关，而 `put` 每条都要开关一次文件。
修法是让 `NativeStorage` 缓存 WAL 的文件句柄 —— 属于 v1.1，见「已知问题」。

## 3. 与 SQLite 的对照

**这不是竞品对比。** SQLite 是成熟二十多年的 C 实现；moonlsm 是教学级 LSM。
拿绝对数字分高下没有意义，这里只是给「50k ops/s 算快还是慢」一个锚点。

### 20 万条 · 每批 1000 条 · 都不同步 fsync

| 指标 | moonlsm | SQLite | 倍数 |
|---|---|---|---|
| 顺序写 | 50 806 ops/s | 424 106 ops/s | 8.3× |
| 随机写 | 23 457 ops/s | 24 737 ops/s | 1.05× |
| 读 P50（命中） | 0.060 ms | 0.011 ms | 5.5× |
| 读 P50（未命中） | 0.053 ms | 0.004 ms | 13× |
| 范围扫描 | 58 834 rows/s | 2 018 033 rows/s | 34× |
| 空间放大 | 1.83× | 1.20× | — |

**这张表有一处对 moonlsm 严重不利，必须先说清楚**：SQLite 在同一个 Python
进程里跑，moonlsm 走「子进程 + 一行 JSON 一条命令」的协议。每读一次都要
一次管道往返 + 一次 JSON 解析。

用「未命中读」可以估出这个协议地板：bloom filter 直接否定，引擎侧几乎不做
任何工作，**0.053 ms 基本就是一次往返的成本**。命中读是 0.060 ms，
也就是说**引擎自身的点查大约 0.01 ms，与 SQLite 的 0.011 ms 同数量级**。

范围扫描的 34 倍差距没这么乐观：即使扣掉协议开销，仍然差一个数量级。
原因在 `Db::scan` 的架构 —— 见下节。

## 4. 已知瓶颈

### 范围扫描（已优化过一轮，仍是最大短板）

第一次跑出来的数字是 **1 250 rows/s**（扫 500 行要 400 ms）。三个原因：

1. **`Db::scan` 对每个 SST 调 `entries()`**，把整个文件解出来再筛。
   改成 `SstReader::scan_range`：用索引做块级剪枝，只解落在区间里的块。
2. **CLI 的 JSON 拼装是 `body = body + ...`**，O(n²) 拷贝。
   500 条 × 115 字节要拷十几 MB。改用 `Buffer`。
3. **`esc` 逐字符拼接**，115 字符的 value 要拷 6.5 KB。
   加了「先扫一遍确认无需转义就直接返回原串」的快路径。

三轮下来 **1 250 → 58 834 rows/s（47×）**。剩下的差距来自架构：
`Db::scan` 仍然是「把每个来源的区间条目全读进数组，再 k 路归并」，
不是流式迭代器。要做到 SQLite 那个量级，需要 `Block` 级别的惰性游标 ——
v1 不做。

### 空间放大 1.83×（20 万条）

三个来源：L0 与 L1 的重叠、墓碑（v1 只在最底层丢弃）、以及每次归并都
整层重写。100 万条时降到 1.13×，因为数据基本都沉到了 L2，重叠少了。

### 单条持久化写 79 ops/s

见第 2 节。根因是每次写都 `fopen`/`fclose` 一次 WAL。

### 顺序写不如随机写（20 万条那组）

`23 457` vs `50 806` —— 随机写比顺序写慢一半，这是**正常**的：随机写那轮
是覆盖写，每个 key 都要在 memtable 的有序数组里二分插入并 memmove。
但 100 万条那组是 `12 724` vs `50 212`，差距拉大到 4 倍，说明数据量上去之后
覆盖写触发的归并更多。

## 5. 测量方法的局限（必须一起看）

1. **协议开销吃掉了小操作的绝大部分。** 所有读延迟数字都包含一次管道往返。
   引擎真实延迟要比表里的小。
2. **`kill -9` 测不出「忘了 fsync」**（ADR-0003）。`sync:false` 那几组数字
   不代表持久化能力，它们代表「引擎本身的吞吐上限」。
3. **单机单次测量，没有取多轮中位数。** 这台机器上同一条命令跑三次，
   吞吐的波动大约 ±10%。
4. **没有和 moonkv 对比。** 计划里有，尚未做。
5. **Windows 的文件系统开销明显高于 Linux**（`fopen` 5.9 ms 这个数字就是
   Windows 特有的）。同样的代码在 Linux 上单条 fsync 会快很多，
   这里没有条件实测，所以不写推测的数字。
