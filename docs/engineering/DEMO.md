# 90 秒演示方案

> 这份文档解决一个问题：**手里有 `demo.py`，但站在镜头前该说什么、什么时候按回车。**
> 逐字稿可以直接念。脚本自身跑完约 23 秒（含第 2 步每行 0.25 秒的停顿），
> 比 90 秒的讲解短得多——机器从来不是瓶颈，**卡的是人的嘴**。
> 所以每一段都留了回车，讲完再按，不要反过来赶。

---

## 1. 先定一件事：这个演示要证明什么

不是「功能列表」，是**一句话**：

> **它怎么证明自己不丢数据。**

原因：嵌入式存储引擎最难的部分不是 put/get 能跑通（那部分一天就能写出来），
是崩溃之后还能不能对上账。90 秒里只要这一件事讲透了，其他都是附属。

所以四步的权重是**递增**的，不是平铺：

| 步骤 | 作用 | 分到的时间 |
|---|---|---|
| 第 1 步 重启还在 | 让人相信这是个真引擎，不是内存 map | 20 秒 |
| 第 2 步 自动归并 | 证明它真的是 LSM，不是「一个文件写到黑」 | 26 秒 |
| 第 3 步 kill -9 | **铺垫杀手锏**：制造一个真正的崩溃 | 16 秒 |
| 第 4 步 逐条校验 | **正面回答**：逐条读回，丢失 0 | 14 秒 |

前两步是「建立可信度」，后两步才是「论证」。讲的时候语气要有区别：
前两步平稳带过，第 3 步开始放慢。

## 2. 录制前检查（这四条任何一条不对，画面就废了）

### 2.1 前置构建

```bash
cd moonlsm
moon build --target native --release
```

`demo.py` 默认找 `_build/native/release/build/cmd/dbcli/dbcli.exe`。
只有 debug 构建的话，把 `--cmd` 指过去，但 release 的数字更接近真实。

### 2.2 终端字体（最容易翻车的一条）

`demo.py` 的表格对齐是按「中文占 2 列」算的（`dwidth()` 用
`unicodedata.east_asian_width`）。如果终端的中文字体宽度不是西文的整 2 倍，
表格会歪。

**验证方法**：跑一次 `python demo.py --no-pause`，看第 2 步那张表——
`L0 / L1 / L2` 三列的表头和数据必须严格对齐。

推荐字体：**Cascadia Mono**（Windows Terminal 默认，中文 fallback 正常对齐）。
不要用 Consolas 单独设中文字体，容易出现 1.5 倍宽。

### 2.3 窗口尺寸与字号

- 终端宽度 **≥ 80 列**（实测最长一行 74 列，含 `dwidth()` 折算）。
  原先表头那行是 **98 列**——因为打印的是 `data` 的绝对路径，在 100 列窗口里
  只差 2 列就折行，而 Windows Terminal 还要占一列滚动条，实际会折。
  已改成相对路径（`数据目录 data`），折行风险消掉了。
- 字号 **18–20 pt**：1080p 下观众能看清，又不至于一屏放不下 8 轮表格
- 关掉侧边栏 / 标签栏，只留内容区

### 2.4 编码

Windows Terminal 默认 UTF-8，一般不用管。如果输出出现乱码：

```powershell
chcp 65001
```

## 3. 90 秒分镜与逐字稿

运行方式（**带 `--pause`**，每段讲完按一次回车）：

```bash
cd benches/python
python demo.py
```

> **提词器**：把 [`prompter.html`](prompter.html) 用浏览器打开，放在另一块屏幕或
> 手机上。空格进下一段、← 回退、R 重置，顶部有总计时和**当前段预算**（超时会变红）。
> 逐字稿就是下面这份，不用两边对照。
>
> 只有一块屏幕怎么办：用手机拍一张 `#3` 这类锚点的页面，或者把浏览器窗口压成
> 窄条贴在屏幕顶部——**别把提词器和终端叠在一起**，录制时会被一起录进去。

### 0:00–0:08 ｜ 开场

**屏幕**：终端停在 `benches/python` 目录，还没执行。

> 「moonlsm，一个用 MoonBit 写的嵌入式 LSM 存储引擎。
> 今天不演示功能列表，只演示一件事——**它怎么证明自己不丢数据**。」

然后回车，脚本开始。

### 0:08–0:28 ｜ 第 1 步：重启还在

**屏幕**：第 1 步输出（`写入 1200 条` → `重启后` → `读回`）

> 「先写 1200 条。注意这里的顺序：先追加 WAL、**fsync 成功之后才回 ack**，
> 最后才改内存表。这个顺序不能反——反了就会出现『读得到、但断电就没了』的脏读，
> 那比直接报错严重得多。
>
> 现在进程退出，重新打开。第一条 key 还在，值逐字节一致。
> 中间这一串是恢复路径：CURRENT → MANIFEST → 加载 SST → 重放 WAL。」

**（回车）**

### 0:28–0:54 ｜ 第 2 步：自动归并

**屏幕**：8 轮表格逐行出现，**约 2.7 秒打完**（每行 0.25 秒，`--row-delay` 可调）

> 这 2.7 秒是**跟着你念的节奏走**的，不是打完再开始念——表格第 1 行出来时
> 你就已经在说「每轮写 600 条再 flush 一次」，说到「第 4 个文件一到」时
> 正好打到第 4 行。念快了会追上表格，念慢了会干等，都正常，不用改口。

> 「接着让它自己合并。每轮写 600 条再 flush 一次，看最左边这列——
> L0 从 1 数到 3，**第 4 个文件一到就触发归并**，L1 出现了。
> 再数到第 8 轮，L1 累计超过 1 MiB，整层沉到 L2。」

（等表格打完再往下。8 行全在屏幕上，后面的话要指着它们说）

> 「两个细节值得说：
>
> 一，归并完 **6000 条还是 6000 条**——归并只做去重，不丢数据。
>
> 二，墓碑只在**最底层**才丢弃。删除标记要是提前扔了，
> 上层还有旧版本，删掉的数据就会复活。所以判断『是不是最底层』这件事不能错。」

**（回车）**

### 0:54–1:10 ｜ 第 3 步：kill -9

**屏幕**：`写入 2xxxx 条，全部拿到 ack` → `kill -9`

> **这个数字每次都不一样**——第 3 步是「1.5 秒内尽量多写」，写到哪算哪。
> 而且它随代码性能变：ADR-0009 之前实测 2 万上下，之后 3.5 万。
> 所以逐字稿里**不出现条数**，只念「每一条都拿到了 ack」，
> 具体数字让观众自己看屏幕。

> 「现在是重点。1.5 秒内尽量多写，每一条都拿到了 ack。
>
> 然后在『一批正在落盘』的瞬间 **kill -9**——不是优雅退出，是直接杀，
> 进程没有任何清理机会。这就是断电的样子。」

**（回车）**

### 1:10–1:24 ｜ 第 4 步：逐条校验

**屏幕**：`校验 2xxxx 条` → `丢失 0 条   值被破坏 0 条`

> 这里的条数必须和第 3 步**一模一样**，对不上就说明统计口径错了，当场停下重录。

> 「重启，把刚才 ack 过的每一条**逐条读回来**。
> 丢失 0，值被破坏 0。
>
> 这就是契约 C1：已经承诺不丢的数据，一条都不能丢。」

**（回车）**

### 1:24–1:30 ｜ 收尾（这一句不要省）

> 「最后诚实说一句：kill -9 只杀进程、**不清操作系统的页缓存**，
> 所以它其实证明不了 fsync。
> fsync 的正确性，是在单元测试里用 WAL 尾部截断注入来验证的。」

**为什么必须说这句**：主动指出自己测试的局限，比等人问出来强。
而且这句话本身就是加分项——说明你知道 `kill -9` 和真断电的区别。

## 4. 怎么录

### 方案 A：Xbox Game Bar（零安装，够用）

1. `Win + G` 打开
2. 点「录制」按钮（或 `Win + Alt + R` 直接开始）
3. 录完在「捕获」里找到 mp4

缺点：只能录单窗口，不能切换；没有鼠标高亮。

### 方案 B：OBS（推荐，可控）

- 源：窗口捕获，选终端窗口
- 输出：1080p / 30fps / mp4
- 好处：可以先试录一遍看构图，不满意直接重来

### 录完之后

- 剪掉开头的鼠标移动和结尾的空白
- **不要加背景音乐**——90 秒的评审视频，音乐只会干扰听旁白
- 不要加转场特效，硬切就行

交之前逐条核一遍，五条全过再交：

| 检查项 | 怎么查 | 合格线 |
|---|---|---|
| 时长 | 播放器看总长 | **≤ 90 秒**（超了先砍第 2 步的停顿，别砍收尾那句） |
| 旁白可懂 | 戴耳机听一遍，**不开字幕** | 每个数字都听得清；听不清就重录，别指望字幕补 |
| 第 3/4 步条数 | 两屏对照 | 必须**完全相同**，不同就是统计口径错了 |
| 文件大小 | `ls -lh` | 平台多限 100 MB；超了按下条压 |
| 画面有没有露出不该露的 | 暂停看四角 | 无用户名、无其他窗口、无通知弹窗 |

压体积（无损可读性，文字边缘不能糊）：

```bash
ffmpeg -i raw.mp4 -c:v libx264 -crf 22 -preset slow -pix_fmt yuv420p \
       -c:a aac -b:a 128k -movflags +faststart demo.mp4
```

> 录屏里全是小字，`-crf` 别超过 24，否则中文笔画会糊成一团。
> `-movflags +faststart` 让网页上能边下边播。

**关于用户名**：`demo.py` 开头原来打的是 `data` 的绝对路径，
`C:\Users\<你的用户名>\...` 会原样进画面。这一行已经改成相对路径
（`数据目录 data`），顺带把「98 列折行」也一起修了——见提交
`fix(demo): 录屏前实测出的两个「画面会废」的坑`。

## 5. 如果现场演示（不录屏）

多准备两件事：

1. **提前跑一遍**，让 `data/` 目录和 release 构建都热起来
   （第一次跑要编译、建目录，会多几秒）
2. **准备兜底截图**：把 `demo.py --no-pause` 的完整输出截成图，
   万一现场环境出问题（端口占用、杀毒软件锁文件），直接切图讲

现场最大的风险不是脚本崩，是**按回车按早了**——表格还没打完就翻页。
所以表格那一段宁可多等两秒。

## 6. 可能被追问的问题

背下来 3 条就够，不用全背。

| 问题 | 回答（一句话） |
|---|---|
| 为什么是三层，不是两层？ | 只有两层时「目标层是不是最底层」恒为真，这个判定永远不会被证伪——而它判错的后果是删掉的数据复活。加 L2 之后两条分支都能真实走到。 |
| 数据损坏了怎么办？ | 九类损坏位置、三条策略：WAL 坏了截断（它只是暂存区），MANIFEST/SST 坏了拒绝启动（它们是已 ack 数据的唯一载体）。判据只有一条——任何自动决策都不能丢已经承诺不丢的数据。 |
| 性能怎么样？ | 100 万条：顺序写 55 658 ops/s，读延迟 P50 0.053 ms，空间放大 1.13×。和 SQLite 同数量级，但**我们的数字里含进程间 JSON 往返**，SQLite 是进程内调用，所以这个对比对我们不利，真实差距更小。 |
| 为什么不做事务？ | 这是嵌入式库，假定单进程独占目录。MVCC 不是这个项目的核心，崩溃一致性才是。 |
| 能跑在单片机上吗？ | **不能，而且「嵌入式」在这里是另一个意思。** 它指 *embedded database*——像 SQLite 那样链接进宿主进程，不是跑在 STM32 上。它要 libc、带 `fsync` 语义的文件系统、一个可调的写缓冲（示例 8 MiB）。**别说「以后可以移植」**，那是另一个项目：换掉整个 `Storage` 层、重设内存预算、自己处理 flash 擦除和掉电检测。 |
| 你们怎么测的？ | 215 条单元测试 + 20 轮 kill -9 + 5000 步随机对拍 + 9 条损坏注入 + 逐字节 fuzz（SST 里任何一个字节坏掉，要么正常打开、要么报 Corruption，绝不 panic）。 |

## 7. 三个不要

1. **不要念代码。** 观众看不清也不需要看清，讲「为什么」不讲「是什么」。
2. **不要说「我们实现了 XXX 功能」。** 功能列表在 README 里，视频里只说证据。
3. **不要省掉收尾那句自我批评。** 那是整段视频里最能体现深度的 6 秒。
